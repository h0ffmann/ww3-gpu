# SCOPE

The work is limited to the single-grid program of WW3 (`ww3_shel`). The test cases come from LabECO's (UFSC) operational forecasting system, which is made available to the project at the start of the schedule, and include regular and unstructured grids. The unstructured ones are triangle meshes that refine the coastline, handled in WW3 by PDLIB (Parallel Decomposition Library). Each case consists of the grid, the switch file, the forcing (the wind fields that drive the model) and the output list. That configuration, as it runs at the laboratory today, and the exact source revision are recorded at the start of the project and kept fixed (frozen) until the end, so that every measurement refers to the same case.

Four rungs are in scope, attempted in order and each gated by a comparison against the frozen reference run:

1. **Build options.** Compiler, optimisation flags, the switch file (in particular the choice between shared-memory, MPI and hybrid builds, and the NetCDF-4 output path), and the MPI and OpenMP layout. This rung changes no source code and is expected to be bit-for-bit reproducible against the reference or, when floating-point reordering is involved, within round-off.
2. **Run configuration.** Domain decomposition across processes, time steps allowed by the CFL condition (the numerical stability limit that ties the time step to the grid spacing), output frequency and output fields, restart strategy, and forcing interpolation. This rung changes only the namelists, the parameter files the model reads when a run starts.
3. **Targeted modern-Fortran refactoring, LLM-assisted** (large language model). Rewriting of the routines that the profile identifies as dominant, typically the source-term integration (`W3SRCE`) and spatial propagation, using standard Fortran 2008/2018 constructs (`do concurrent`, explicit interfaces, contiguous arrays) without altering the numerical algorithm and within a tolerance defined per output field. The migration is carried out with an LLM-based coding assistant directed by the student, in the role Koldunov et al. [-@koldunov2026] describe for FESOM2, an ocean circulation model: the assistant proposes the translation, routine by routine, while the student and the co-advisor are responsible for the review and the validation. Prompts, the reviewed diff and the parity test results are versioned with the code, and no routine is accepted without passing the per-field comparator described in the methodology.
4. **Rewriting kernels in C++/Kokkos and running them on a GPU (NVIDIA H100).** Kokkos is a C++ performance-portability library: the same source, written once with its parallel abstractions (`parallel_for`, `parallel_reduce`) and data abstractions (`View`, which fixes the memory layout per architecture), is compiled to the native backend of each machine: Serial and OpenMP on CPUs, CUDA on NVIDIA GPUs, HIP on AMD and SYCL on Intel [@trott2022]. It is the same layer named for WAVEWATCH IV [@on528], which makes the artefacts reusable. Substitution is incremental and bottom-up: the routines that remain dominant after rung 3 become Kokkos kernels, called from Fortran through `bind(C)` interfaces and kept in the same binary as the original routine, behind a run-time switch. It starts with the nonlinear interaction term (the energy exchange between waves of different frequencies) and follows the profile order. This is not a full port of the model: the state stays in Fortran, and the CPU–GPU transfer cost per time step is measured and reported. A GPU kernel reaches the laboratory's operational configuration if, and only if, it reduces the run time of the operational case and meets the same parity criteria as the earlier rungs.

The order of the rungs is part of the scope: rungs 1 and 2 are exhausted before any code change, and rung 3 before rung 4, so that the C++/Kokkos rewrite is only attempted on routines whose residual cost has already been demonstrated.

NOAA is currently rewriting the model in C++ under the name WAVEWATCH IV (WW4) [@ww4repo]. This proposal is conducted independently of that repository and does not intend to contribute to it: it adopts only the WW4 test structure (unit and integration levels in GoogleTest) for the rewritten kernels, so that the artefacts remain useful in a future migration.

Out of scope are the multi-grid program (`ww3_multi`), coupling to other models, data assimilation, and any change to the physics parameterisations.
