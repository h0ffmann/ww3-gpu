# SCOPE

The work is limited to WW3's single-grid program (`ww3_shel`). The model's pre-processors, such as `ww3_grid`, are used as they are, and only their input files may change. The test cases come from LabECO's operational forecasting system, which will be made available at the start of the schedule, and include regular and unstructured grids. Unstructured grids are triangle meshes that allow finer resolution near the coast; in parallel runs, WW3 splits them among processes with the PDLIB library (Parallel Decomposition Library). Each case consists of the grid, the switch file, the forcing (the external fields that drive the model, mainly wind) and the output list. At the start of the project, the configuration of each case, as it runs at the laboratory today, and the exact source revision will be recorded and kept fixed (frozen) until the end of the work, so that every measurement always refers to the same cases. WW3's official regression tests serve only as a validation instrument.

Four rungs are in scope, carried out in this order and each validated against the reference run:

1. **Build options.** The choice of compiler and optimisation flags; of the switch file, which includes forcing interpolation, the output format (NetCDF-4) and the parallelisation mode (shared memory, MPI or hybrid and, on the unstructured grid, domain decomposition through PDLIB); and of the layout of MPI processes and OpenMP threads. This rung does not change the source code. Results are expected to be bit-for-bit identical to the reference or, when the compiler reorders floating-point operations, to differ only at round-off level.
2. **Run configuration.** Tuning of the time steps, within the numerical stability limit given by the Courant–Friedrichs–Lewy (CFL) condition, which relates the time step, the grid spacing and the propagation speed of the waves; of the output frequency and field list; and of the restart strategy. This rung changes only the namelists, the parameter files read by WW3's programs.
3. **Targeted modern-Fortran refactoring, assisted by a large language model (LLM).** Rewriting of the routines the performance profile shows as dominant, typically the source-term integration (`W3SRCE`) and propagation on the regular grid, using Fortran 2008/2018 constructs (`do concurrent`, explicit interfaces, contiguous arrays) without changing the numerical algorithm. The coding assistant will propose the translation, routine by routine, and the student and the co-advisor will be responsible for the review and the validation, as in the work of Koldunov et al. [-@koldunov2026] on FESOM2, an ocean circulation model.
4. **Rewriting kernels in C++/Kokkos and running them on a GPU (NVIDIA H100).** Kokkos is a C++ performance-portability library in which the same source code is compiled for CPUs and for GPUs from different vendors [@trott2022]. The routines that remain dominant after rung 3 will be rewritten, one at a time, as Kokkos kernels called from Fortran, and the original routine will stay in the same executable, selectable at run time. The first will be the nonlinear interaction term, which represents the energy exchange between waves of different frequencies, chosen because it is self-contained and can be tested on a synthetic spectrum; the next ones will depend on the profile. The project does not plan to move the whole model to the GPU: the model state will stay in Fortran, in CPU memory, and the cost of moving data between CPU and GPU at every time step will be measured and reported.

The order of the rungs is part of the scope. Rungs 1 and 2 will be exhausted before any code change, and rung 3 before rung 4, so that the C++/Kokkos rewrite is only done on routines whose cost after the earlier rungs has been measured. Source terms are computed point by point and are therefore the same on both grid types; in rungs 3 and 4 they will be handled on both. Propagation on the unstructured grid uses its own routines, tied to PDLIB, and will be kept as it is.

In parallel, NOAA is developing WAVEWATCH IV (WW4), a rewrite of the model with a C++ core [@on528; @ww4repo]. This project is independent of that effort and does not intend to contribute code to it. From WW4 it adopts only the test structure (unit and integration levels, in GoogleTest) for the rewritten kernels, so that they can be reused in a future migration.

Out of scope are the multi-grid program (`ww3_multi`), coupling with other models, data assimilation, and any change to the physics parameterisations, that is, to the formulations of the source terms.
