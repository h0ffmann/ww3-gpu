# SCOPE

The work is limited to the single-grid driver of WW3 (`ww3_shel`), with the test cases coming from the operational forecasting system of LabECO (UFSC), which is made available to the project at the start of the schedule: its grid, its switch file, its forcing and its output list. That configuration and the exact source revision are frozen and documented at the start of the project, so that every measurement refers to the same case. The regular grid is the reference case; unstructured grids (PDLIB) enter the scope only if the laboratory's operational configuration requires them, and in that case the same measurement procedure applies to them.

Four rungs are in scope, attempted in order and each gated by a comparison against the frozen reference run:

1. **Build options.** Compiler, optimisation flags, the switch file (in particular the choice between shared-memory, MPI and hybrid builds, and the NetCDF-4 output path), and the MPI and OpenMP layout. This rung changes no source code and is expected to be bit-for-bit reproducible against the reference or, when floating-point reordering is involved, within round-off.
2. **Run configuration.** Domain decomposition, time steps allowed by the CFL condition, output frequency and output fields, restart strategy, and forcing interpolation. This rung changes namelist inputs only.
3. **Targeted modern-Fortran refactoring, LLM-assisted.** Rewriting of the routines that the profile identifies as dominant, typically the source-term integration (`W3SRCE`) and spatial propagation, using standard Fortran 2008/2018 constructs (`do concurrent`, explicit interfaces, contiguous arrays) without altering the numerical algorithm and within a tolerance defined per output field. The migration is carried out with an LLM-based coding assistant directed by the student, in the role Koldunov et al. [-@koldunov2026] describe for FESOM2: the model proposes the translation, routine by routine, while the student and the co-advisor own the review and the validation. What enters the repository is the evidence, not the suggestion: prompts, the reviewed diff and the parity test results are versioned with the code, and no routine is accepted without passing the per-field comparator described in the methodology.
4. **Rewriting kernels in C++/Kokkos and running them on a GPU (NVIDIA H100).** Kokkos is a C++ performance-portability library: the same source, written once with its parallel abstractions (`parallel_for`, `parallel_reduce`) and data abstractions (`View`, which fixes the memory layout per architecture), is compiled to the native backend of each machine — Serial and OpenMP on CPUs, CUDA on NVIDIA GPUs, HIP on AMD and SYCL on Intel [@trott2022]. It is the same layer named for WAVEWATCH IV [@on528], which makes the artefacts reusable. Substitution is incremental and bottom-up: the routines that remain dominant after rung 3 become Kokkos kernels, called from Fortran through `bind(C)` interfaces and kept in the same binary as the original routine, behind a run-time switch. It starts with the nonlinear interaction term and follows the profile order. This is not a full port of the model: the state stays in Fortran and the CPU–GPU transfer cost per time step is measured and reported. A GPU kernel reaches the laboratory's operational configuration if, and only if, it reduces the run time of the operational case and meets the same parity criteria as the earlier rungs.

The order of the rungs is part of the scope: rungs 1 and 2 are exhausted before any code change, and rung 3 before rung 4, so that the C++/Kokkos rewrite is only attempted on routines whose residual cost has already been demonstrated.

There is currently an initiative to convert the code to C within the WAVEWATCH IV project [@ww4repo]. This proposal is conducted independently of that repository and does not intend to contribute to it: it adopts only the WW4 test structure (unit and integration levels in GoogleTest) for the rewritten kernels, so that the artefacts remain useful in a future migration.

Out of scope are the multi-grid driver (`ww3_multi`), coupling to other models, data assimilation, and any change to the physics parameterisations.
