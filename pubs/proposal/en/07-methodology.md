# METHODOLOGY

The project follows the principle of measuring before optimising: no optimisation is attempted before the reference run is reproducible and profiled, and none is accepted without a parity check against it.

**Reference and benchmark.** The laboratory's operational case is captured as a self-contained test: input files, forcing for a fixed period, switch file, namelists and reference results. The same is done with the official regression test closest to the operational configuration. The benchmark script records time per phase, processes and threads, compiler and options and the source revision, and produces a table that can be attached to the reports.

**Profiling.** The reference run is profiled with `gprof` or `perf` on one, four and sixteen MPI processes, with communication time recorded separately. The result is a time-per-routine table, grouped into the phases of the time loop, which sets the order of the refactoring and the baseline for every later measurement.

**Parity criteria.** In rungs 1 and 2 the results are compared bit for bit with WW3's own regression matrix, used as it is; when a compiler option reorders floating-point operations, the comparison uses per-field tolerances (for example significant wave height, peak period and mean direction) proposed by the student and approved by the co-advisor. For rungs 3 and 4 the project adds what the matrix does not offer: a per-field comparator that reads the NetCDF outputs of two runs and applies tolerances recorded in a versioned file, and per-routine unit tests that run the original and the rewritten routine on inputs captured from the operational case. A change that fails the criterion is not incorporated.

**Rungs.** Build options are explored first, as a matrix of compiler, options and parallel layout. Run configuration follows, varying one namelist parameter at a time. The Fortran refactoring addresses the routines at the top of the profile, one at a time, in a fork that keeps the original routine reachable through a run-time switch in the same binary. Only then does rung 4 begin, restricted to the routines whose residual cost the updated profile still shows as dominant.

**Kernel interoperability and testing.** Each C++/Kokkos kernel is exposed to Fortran through an `ISO_C_BINDING`/`bind(C)` interface, and the original routine stays in the binary behind the same run-time switch, so that the regression matrix and the comparator exercise both paths without recompiling. The layout of the Kokkos `View`s reproduces that of WW3's spectral arrays, so that the CPU call copies no data. The translation follows the FESOM2 recipe [@koldunov2026]: a literal translation to C, checked against the Fortran on captured inputs; a Kokkos version whose Serial backend must be bit-for-bit identical to the C one; and only then the CUDA backend on the H100, compared statistically, with CPU–GPU traffic per time step recorded. The tests follow the WW4 structure: level L1, a unit test of the kernel on a synthetic (JONSWAP) spectrum with declared and justified tolerances, in GoogleTest; level L2, a rerun of the closest regression case and of the operational case, comparing WW3 and WW3+Kokkos with the per-field comparator. An LLM-based coding assistant is used for the translation under the same rules, with the student and the co-advisor responsible for validation; prompts and parity evidence are versioned with the code. The decision to take a kernel into operation is made with LabECO on two pieces of evidence: the timing table of the operational case, with and without the kernel, and the parity report.

**Tooling and reproducibility.** All work is done in the open `ww3-gpu` repository [@wwlab], which provides the pinned toolchain, the build and regression scripts, the model as a submodule at a pinned revision, and continuous integration, so that any measurement can be repeated by the laboratory on its own machines. Results are recorded as tables and figures generated by scripts, never by hand.

**Deliverables and validation.** The deliverables are the configuration record, the benchmark and profile tables, the best documented build, the per-field comparator and the unit tests, the Kokkos kernels with their parity and timing evidence, and the final report with the operational recommendation. Scientific validation rests with the co-advisor at LabECO, who sets the tolerances and reviews the parity evidence; engineering validation rests with the repository's automated tests and independent reruns at the laboratory.

**Risks.** The main one is silent divergence of results after a rewrite, mitigated by the parity criteria and the per-routine tests. The second is rung 4 consuming the time of the earlier ones, mitigated by the fixed order of the rungs and by the rule of rewriting only a routine whose residual cost has been measured. The third is the GPU gain being bounded by data traffic while the state remains in Fortran; in that case the result is the measurement of that bound and a recommendation not to run on GPU. The fourth is the operational grid being unstructured; in that case rungs 3 and 4 are restricted to the source terms.
