# METHODOLOGY

The project will follow the principle of measuring before optimising and will advance in test-and-validation cycles. Two quantities will be measured in every cycle: run time, total and per phase of the time loop, expressed as run time per forecast hour; and agreement of the results, that is, the difference between the fields produced by the changed run and by the reference run. In each cycle a single element will be changed (an option, a parameter or a routine), and the tests will run from the cheapest to the most expensive: first the isolated routine, when code has changed, then a simplified grid and, last, the operational case. The results will then be compared with the reference; from rung 4 onwards, the CPU run and the GPU run of the same code will also be compared on the simplified grid. A change that passes will be incorporated and become the baseline of the next cycle, and one that fails will go back to rewriting or be discarded.

**Reference cases and simplified grids.** The laboratory's operational cases, on a regular and on an unstructured grid, will be captured as self-contained tests, with input files, forcing for a fixed period, switch file, namelists and reference results. For each grid type a simplified grid will also be defined, a reduced domain derived from the operational case or from the closest official regression test, which runs in a few minutes on both CPU and GPU and will be used in every test cycle. The simplified grid only speeds up the cycles and does not replace the operational case in any reported measurement. The benchmark script will record time per phase, the number of processes and threads, the compiler and its options and the source revision, and will produce a table that can be attached to the reports.

**Profiling.** The performance profile of the reference run will be taken with two complementary tools. `gprof` instruments the executable at compile time (the `-pg` option) and produces the call graph, with the time accumulated in each routine and in the routines it calls [@graham1982]. `perf`, distributed with the Linux kernel, periodically samples the run through the processor's performance counters, without recompiling the model, and attributes time to routines and source lines [@perf]. The former gives the call structure, and the latter confirms the timings without the interference of instrumentation. Measurements will be taken on one, four and sixteen MPI processes, with communication time recorded separately. The result will be a time-per-routine table, grouped by the phases of the time loop, which will set the order of the refactoring and serve as the baseline for every later measurement.

**Build and configuration rungs.** The rungs are the four defined in the scope, executed in the same order. In rung 1, build options will be explored as a matrix of compiler, options and parallel layout, which includes, on the unstructured grid, building with PDLIB. In rung 2, the starting point will be a single set of namelists per case, the operational one, frozen at the start of the project and also used in every other rung. From it, only the parameters listed in the scope, which affect performance without changing the physics parameterisations, will be varied, one at a time. The outcome will be at most a second set of namelists, documented and proposed to the laboratory.

**Rewriting rungs.** In rung 3, the Fortran refactoring will address the routines at the top of the profile, one at a time, in a fork of the code that keeps the original routine in the same executable, selectable at run time. Only then will rung 4 begin, restricted to the routines the updated profile still shows as dominant.

**Agreement criteria and order of the tests.** In rungs 1 and 2, WW3's own regression matrix will be used as it is, and the outputs of the operational cases and of the simplified grids will be compared bit for bit, file by file, with those of the reference run. When a compiler option reorders floating-point operations, the comparison will move to the field-by-field comparator described next, with tolerances set by the LabECO research group for each field, such as significant wave height, peak period and peak direction, which are the period and direction of the waves that carry the most energy. In rungs 3 and 4, where the code changes, the project will add what the matrix does not offer, at two levels applied in this order. First, before any run of the full model, per-routine unit tests will run the original and the rewritten routine on inputs captured from the operational case and compare the output arrays in memory, which detects an error in seconds and already points to the routine responsible. Then a field-by-field comparator will read the NetCDF outputs of two full runs, first on the simplified grid and then on the operational case, and apply tolerances recorded in a versioned file. Since the NetCDF file is the final product of the chain, this test comes last. A change that fails at any level will not be incorporated: it will go back to rewriting and repeat the cycle from the unit tests.

**Kernel interoperability and testing.** Each C++/Kokkos kernel will be exposed to Fortran through an `ISO_C_BINDING`/`bind(C)` interface, and the original routine will stay in the executable, selectable by the same option, so that the regression matrix and the comparator can test both paths without recompiling. The layout of the Kokkos `View`s will reproduce that of WW3's spectral arrays, so that the CPU call copies no data. The translation will follow the method applied to FESOM2 [@koldunov2026]. First, a literal translation to C, checked against the Fortran on captured inputs. Next, a Kokkos version whose Serial backend must reproduce the C bit for bit. Only then will the CUDA backend run on the H100, compared statistically with the CPU run, first on the simplified grid and then on the operational case, with the volume of data moved between CPU and GPU at every time step recorded. The tests will follow the WW4 structure. At level L1, each kernel will have a GoogleTest unit test on a synthetic wind-sea spectrum with the empirical JONSWAP (Joint North Sea Wave Project) shape [@hasselmann1973], and with declared and justified tolerances. At level L2, the simplified grid and the operational case will be rerun, comparing the original WW3 and WW3 with Kokkos through the field-by-field comparator. The decision to take a kernel into operation will be made with LabECO on two pieces of evidence: the timing table of the operational case, with and without the kernel, and the agreement report.

**LLM-assisted activities.** An LLM-based coding assistant, directed by the student, will be used in four activities: reading and documenting WW3's dominant routines, to map their dependencies on global variables before the rewrite; proposing the modern-Fortran refactoring, routine by routine, in rung 3; the literal translation from Fortran to C and from C to C++/Kokkos in rung 4, following the method of Koldunov et al. [-@koldunov2026]; and generating the unit tests and the scripts that capture inputs and compare outputs. In all of them the assistant proposes and does not decide. None of its output will be accepted without meeting the same agreement criteria required of hand-written code, and the student and the co-advisor will be responsible for the code review and for the agreement evidence. Prompts, the reviewed diff and the agreement evidence will be versioned with the code. The final report will record, per activity, what the assistant produced, what was corrected by hand and what was discarded, as an assessment of the method itself.

**Tooling and reproducibility.** The code, the tooling and the tests will be versioned in the public `ww3-gpu` repository [@wwlab], which provides the pinned toolchain, the build and regression scripts, the model as a submodule at a pinned revision, and continuous integration, so that any measurement can be repeated by the laboratory on its own machines. The operational configuration and LabECO's data, as well as results not yet published, will stay outside the public repository, in a restricted location set by the laboratory, until the defence of the undergraduate project or the submission of a paper by the research group, whichever comes first, unless the advisors decide otherwise. Results will be recorded as tables and figures generated by scripts.

**Deliverables and validation.** The deliverables are the configuration record, the benchmark and profile tables, the best documented build, the field-by-field comparator and the unit tests, the Kokkos kernels with their agreement and timing evidence, and the final report with the operational recommendation. Scientific validation will rest with the LabECO research group, which sets the tolerances and reviews the agreement evidence; engineering validation, with the repository's automated tests and independent reruns at the laboratory.

**Risks.** The main risk is silent divergence of results after a rewrite, mitigated by the agreement criteria and the per-routine tests. The second is rung 4 consuming the time of the earlier ones, mitigated by the fixed order of the rungs and by the rule of rewriting only routines whose cost after the earlier rungs has been measured. The third is the GPU gain being bounded by data transfer while the state remains in Fortran. In that case, the result will be the measurement of that bound, a recommendation not to run on the GPU in that configuration, and the next step, which is keeping the data on the GPU from one time step to the next.
