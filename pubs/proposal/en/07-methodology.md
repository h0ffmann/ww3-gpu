# METHODOLOGY

The project follows the principle of measuring before optimising and advances in test-and-validation cycles. Two quantities are measured in every cycle: run time, total and per phase of the time loop, expressed as run time per forecast hour; and parity of the results, that is, the difference between the fields produced by the changed run and by the reference run. Every cycle has the same shape. A single element is changed (an option, a parameter or a routine). The tests run from the cheapest to the most expensive: the isolated routine, when code has changed, a simplified grid and, last, the operational case. The results are compared with the reference; from rung 4 onwards, in addition to the comparison with the reference, the CPU run and the GPU run of the same code are always compared on the simplified grid. A change that passes is incorporated and becomes the baseline of the next cycle; one that fails returns to rewriting or is discarded.

**Reference and benchmark tests.** The laboratory's operational case is captured as a self-contained test: input files, forcing for a fixed period, switch file, namelists and reference results. Alongside it, a simplified grid is defined: a reduced domain, derived from the official regression test closest to the operational configuration, which runs in minutes on both CPU and GPU and is used in every test cycle. The simplified grid is a cycle instrument: it does not replace the operational case in any reported measurement. The benchmark script records time per phase, processes and threads, compiler and options and the source revision, and produces a table that can be attached to the reports.

**Profiling.** The reference run is profiled with two complementary tools. `gprof` instruments the executable at compile time (the `-pg` option) and produces the call graph, with the time accumulated in each routine and in the routines it calls [@graham1982]. `perf`, distributed with the Linux operating-system kernel, periodically samples the run from the processor's performance counters, without recompiling the model, and attributes time to routines and source lines [@perf]. The former gives the call structure; the latter confirms the timings without the perturbation introduced by instrumentation. Measurements are taken on one, four and sixteen MPI processes, with communication time recorded separately. The result is a time-per-routine table, grouped into the phases of the time loop, which sets the order of the refactoring and the baseline for every later measurement.

**Build and configuration rungs.** The rungs are the four defined in the scope, executed in the same order. In rung 1, build options are explored as a matrix of compiler, options and parallel layout. In rung 2, the starting point is a single namelist: the operational one, frozen at the start of the project, which is also the namelist of every other rung. From it, only the restricted set of parameters listed in the scope, which affects performance without touching the physical parameterisations, is varied, one parameter at a time. The outcome is at most a second namelist, documented and proposed to the laboratory.

**Rewriting rungs.** In rung 3, the Fortran refactoring addresses the routines at the top of the profile, one at a time, in a fork that keeps the original routine reachable through a run-time switch in the same binary. Only then does rung 4 begin, restricted to the routines whose residual cost the updated profile still shows as dominant.

**Parity criteria and order of the tests.** In rungs 1 and 2, WW3's own regression matrix is used as it is, and the outputs of the operational case and of the simplified grid are compared bit for bit, file by file, with those of the reference run; when a compiler option reorders floating-point operations, the comparison moves to the per-field comparator described next, with per-field tolerances (for example significant wave height, peak period and peak direction), set for each field by the LabECO research group. In rungs 3 and 4, where the code changes, the project adds what the matrix does not offer, at two levels applied in this order. First, before any run of the full model, per-routine unit tests run the original and the rewritten routine on inputs captured from the operational case and compare the output arrays in memory, which detects an error in seconds and locates it in the routine. Then a per-field comparator reads the NetCDF outputs of two full runs, on the simplified grid and then on the operational case, and applies tolerances recorded in a versioned file. Since NetCDF is the final product of the chain, this is the last test, not the first. A change that fails at any level is not incorporated: it returns to rewriting and repeats the cycle from the unit tests.

**Kernel interoperability and testing.** Each C++/Kokkos kernel is exposed to Fortran through an `ISO_C_BINDING`/`bind(C)` interface, and the original routine stays in the binary behind the same run-time switch, so that the regression matrix and the comparator exercise both paths without recompiling. The layout of the Kokkos `View`s reproduces that of WW3's spectral arrays, so that the CPU call copies no data. The translation follows the FESOM2 recipe [@koldunov2026]: a literal translation to C, checked against the Fortran on captured inputs; a Kokkos version whose Serial backend must be bit-for-bit identical to the C one; and only then the CUDA backend on the H100, compared statistically with the CPU run, first on the simplified grid and then on the operational case, with CPU–GPU traffic per time step recorded. The tests follow the WW4 structure: level L1, a unit test of the kernel on a synthetic (JONSWAP) spectrum with declared and justified tolerances, in GoogleTest; level L2, a rerun of the simplified grid and of the operational case, comparing WW3 and WW3+Kokkos with the per-field comparator. The decision to take a kernel into operation is made with LabECO on two pieces of evidence: the timing table of the operational case, with and without the kernel, and the parity report.

**LLM-assisted activities.** An LLM-based coding assistant, directed by the student, is used in four activities: reading and documenting WW3's dominant routines, to map their dependencies on global state before the rewrite; proposing the modern-Fortran refactoring, routine by routine, in rung 3; the literal translation from Fortran to C and from C to C++/Kokkos in rung 4, following the recipe of Koldunov et al. [-@koldunov2026]; and generating the unit tests and the scripts that capture inputs and compare outputs. In all of them the assistant proposes and does not decide. None of its output is accepted without meeting the same parity criteria applied to hand-written code, and the student and the co-advisor are responsible for the code review and for the parity evidence. Prompts, the reviewed diff and the parity evidence are versioned with the code. The final report records, per activity, what the assistant produced, what was corrected by hand and what was discarded, as an assessment of the method itself.

**Tooling and reproducibility.** All work is versioned in the `ww3-gpu` repository [@wwlab], which provides the pinned toolchain, the build and regression scripts, the model as a submodule at a pinned revision, and continuous integration, so that any measurement can be repeated by the laboratory on its own machines. The code, the tooling and the tests are open. The operational configuration and LabECO's data, as well as results not yet published, remain restricted to the laboratory until the defence of the undergraduate project or the submission of a paper by the research group, whichever comes first, unless the advisors decide otherwise. Results are recorded as tables and figures generated by automated scripts.

**Deliverables and validation.** The deliverables are the configuration record, the benchmark and profile tables, the best documented build, the per-field comparator and the unit tests, the Kokkos kernels with their parity and timing evidence, and the final report with the operational recommendation. Scientific validation rests with the LabECO research group, which sets the tolerances and reviews the parity evidence; engineering validation rests with the repository's automated tests and independent reruns at the laboratory.

**Risks.** The main one is silent divergence of results after a rewrite, mitigated by the parity criteria and the per-routine tests. The second is rung 4 consuming the time of the earlier ones, mitigated by the fixed order of the rungs and by the rule of rewriting only a routine whose residual cost has been measured. The third is the GPU gain being bounded by data traffic while the state remains in Fortran; in that case the result is the measurement of that bound and a recommendation not to run on GPU. The fourth is the operational grid being unstructured; in that case rungs 3 and 4 are restricted to the source terms.
