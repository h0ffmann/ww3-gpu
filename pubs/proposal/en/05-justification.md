# JUSTIFICATION

Wave models are driven by the wind forecast by atmospheric models. Because those models are governed by nonlinear equations, the wind forecast, and with it the wave forecast, loses quality as the forecast horizon grows. Campos et al. [-@campos2020] compared the NCEP ensemble forecast system with measurements from four altimeter satellites, which record wave height from space, and showed that the error grows along the forecast days. For that reason, operational systems update the forecast several times a day and use ensemble forecasting, in which the model is run many times with small perturbations of the initial conditions and the forcing. The mean of the runs tends to err less than a single run [@farina2002]. In the NCEP system, the ensemble mean cut the random component of the error in significant wave height, which roughly corresponds to the mean of the highest third of the waves, from 1.8 m in the control run (no perturbations) to 1.3 m [@campos2020].

Cycle frequency, resolution, and the number of nested grids and of ensemble members are bounded by the run time of each forecast and by the computing resources available. NCEP, for instance, runs GFS-Wave, its global wave forecast system, four times a day (00, 06, 12 and 18 UTC) on global grids of 0.16° and 0.25° with finer regional grids nested inside, plus GEFS-Wave, the ensemble version, with 30 members at 0.25°, both out to 384 h [@emcwaves].

The same holds for LabECO. ReNOMO, funded by the CNPq/MCTI/Finep 062/2022 call, integrates ocean observation, quality control and operational products for the South Atlantic and the Brazilian coast [@renomo]. For the wave field that feeds those products, a shorter cycle allows earlier delivery, a finer grid at the same deadline, or ensemble members to quantify uncertainty.

WW3 was designed for the supercomputers of the last two decades, and NOAA itself acknowledges that its parallel concepts and its data structures, inherited from the transition to Fortran 90, have not kept up with the hardware [@on525]. High-performance computing is moving from general-purpose processors to heterogeneous nodes with many cores and accelerators such as GPUs. That shift has led weather, ocean and climate prediction codes to revisit their structure [@bauer2021] and motivated performance-portability layers such as Kokkos [@trott2022].

Rungs 1 and 2 come first because they require no change to the code. Moreover, according to the model's manual, part of the performance depends on choices made outside the source code. The switch file and the compiler options determine which code is compiled and how, and the layout of MPI processes and OpenMP threads determines how much time is spent exchanging spectra between processes rather than computing them [@ww3manual]. In an installation configured once, when the model was deployed, and not revisited since, part of the run time may be due to the configuration rather than to the code. These rungs cost little, only machine hours, and produce the two instruments the later rungs depend on: a reproducible benchmark, which measures run time the same way every time, and a performance profile, which shows in which routines that time is spent. Without these, there is no way to know how much time can still be saved, or in which routines, so rewriting code before them is not justified.

Rung 3 is justified by the structure of the code. The profile published by Ikuyajolu et al. [-@ikuyajolu2023] shows that the source-term integration dominates WW3's run time, with propagation second, and that the routines involved use large local arrays and global variables declared in modules, which hinders both vectorisation and execution on a GPU. Rewriting these routines in modern Fortran, preserving the algorithm and the arithmetic, is engineering work of known risk, with directly measurable gain in the model the laboratory operates. It also prepares the next rung, since a routine with an explicit interface and contiguous data in memory can be replaced by a kernel.

Rung 4 answers a question from the laboratory itself: whether an H100 GPU can accelerate the model in operation. Upstream WW3 offers no GPU execution [@ww3repo]. The only published port on record moved the source terms to the GPU with OpenACC directives and obtained a speed-up of about 1.3 times per node, limited by data transfer between CPU and GPU at every time step [@ikuyajolu2023]. By contrast, the authors of WAM6-GPU, the GPU version of another third-generation wave model, restructured the whole model to keep all fields in GPU memory and obtained an order-of-magnitude gain on a multi-GPU node [@yuan2024]. The two results indicate that the gain depends on the data staying on the GPU: when the model state lives on the CPU and must be copied at every step, the transfer limits the gain. Even so, this project will keep the state in Fortran, for three reasons. Moving the whole model does not fit the timeline of an undergraduate project; replacing one routine at a time allows each kernel to be validated in isolation, by comparison with the original code; and measuring the cost of that transfer on the H100 is itself a useful result for the laboratory. The outcome of rung 4 may therefore be negative, that is, a kernel may become faster on the GPU without the cycle getting shorter. The translation will follow the method of Koldunov et al. [-@koldunov2026], work not yet peer-reviewed, who translated some 74 thousand lines of FESOM2 Fortran to C and then to C++/Kokkos in weeks, with an expert-directed LLM coding assistant, two-stage literal translation and validation in successive levels. The criterion for taking a kernel into operation will be the same as for the other rungs: measured gain and results within tolerance.

**State of WW3 testing.** The proposed validation rests on the model's own test infrastructure, as it stood on the `develop` branch (version 7.14) in September 2026 [@ww3repo]. WW3 has 62 regression test cases in `regtests/`, run by a matrix of scripts that compiles switch combinations, compares the outputs of two runs file by file with `cmp` and `diff`, and classifies each case as identical or not. The matrix includes variants that check bit-for-bit reproducibility after a restart and with different numbers of threads and of processes. There is no tolerance-based comparison: any numerical difference is recorded as a failure, and it falls to the reviewer to judge whether it is acceptable. The unit tests, introduced in 2023, cover input and output only (five programs, via CTest). That picture defines how the project will validate each rung. Rungs 1 and 2 will be validated with the model's own matrix, for which the bit-for-bit criterion is enough, while rungs 3 and 4 require a field-by-field comparator with tolerances and per-routine unit tests, which WW3 does not have and which the project will build.

**State of WW4.** The WAVEWATCH IV repository was created in November 2025 and, on 15 September 2026, still had no published release [@ww4repo]. Phase II of the project, which dealt with languages, governance and architecture, was completed in March 2026 [@on528], adopting a C++ core that has no source terms or propagation yet. The test strategy defines four levels in GoogleTest, of which only the first two exist, unit (L1) and integration (L2); the functional (L3) and regression (L4) levels, which would replace the WW3 matrix, have not been written yet. The CPU–GPU architecture is still open, and using Kokkos as the data abstraction layer is only a proposal [@ww4repo]. The published plan expected the first public release in mid-2027 and only ends WW3 support once WW4 is mature [@on525]. Two consequences follow: WW3 will remain the laboratory's operational model for some years, which justifies optimising it, and the kernels rewritten here, in Kokkos and with L1 and L2 tests in the WW4 style, can contribute to the WW4 architecture discussion without duplicating it.
