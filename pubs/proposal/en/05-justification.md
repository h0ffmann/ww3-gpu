# JUSTIFICATION

Wave forecasts depend on the wind forecast that drives them and, like it, lose quality with lead time. Compared with four altimeter satellite missions, which measure wave height from space, the NCEP ensemble forecast shows the error growing along the forecast days [@campos2020]. Operational centres respond by running the model more often each day and in ensemble: several runs with small perturbations of the initial conditions and the forcing, whose mean errs less than a single run [@farina2002; @campos2020]. In the NCEP system, the ensemble mean cuts the scatter error of significant wave height (roughly the mean height of the highest third of the waves, the quantity most used in forecasting) from 1.8 m in the control run to 1.3 m [@campos2020]. NCEP runs GFS-Wave, its global wave forecast system, four times a day (00, 06, 12 and 18 UTC) out to 384 h on global grids of 0.16° and 0.25° with finer regional grids nested inside, and GEFS-Wave, the ensemble version, with 30 members at 0.25° out to 16 days [@emcwaves]. Cycle frequency, resolution, number of nested grids and of members: each of those choices is bounded by the wall-clock time of a forecast and by the computing resources available.

The same holds for LabECO. ReNOMO, funded by the CNPq/MCTI/Finep 062/2022 call, integrates ocean observation, quality control and operational products for the South Atlantic and the Brazilian coast [@renomo]. For the wave field that feeds the ReNOMO operational product, a shorter cycle allows earlier delivery, a finer grid at the same deadline, or ensemble members to quantify uncertainty. WW3, whose parallelisation and build architecture is documented in its manual [@ww3manual], was designed for the supercomputers of the last two decades and carries choices, in its build system, its data layout and its parallel decomposition, that are not necessarily the best ones for present-day high-performance computing. That field is moving from general-purpose processors to heterogeneous nodes with many cores and accelerators (GPUs), which forces weather, ocean and climate prediction codes to revisit their structure [@bauer2021] and motivated performance-portability layers such as Kokkos [@trott2022].

Rungs 1 and 2 come first because they require no change to the code and because the model's manual shows that part of the performance is decided outside the source code: the switch file and the compiler options determine which code is compiled and how, and the layout of MPI processes and OpenMP threads determines how much time is spent exchanging spectra between processes rather than computing them [@ww3manual]. In an installation configured once, when the model was deployed, and not revisited since, part of the run time may be due to the configuration rather than to the code. These rungs cost little (machine hours, no rewritten routine) and produce the two instruments the later rungs depend on: a reproducible benchmark, which measures run time the same way every time, and a profile, which shows in which routines that time is spent. Only after them is it known how much run time is left to gain and in which routines, and only then is a rewrite justified.

Rung 3 is justified by the structure of the code. Published profiling of WW3 shows that the source-term integration dominates the run time, with propagation second, and that the routines involved use large local arrays and module-level global state, which hinders both vectorisation and moving the computation to the GPU (offloading) [@ikuyajolu2023]. Rewriting them in modern Fortran, preserving the algorithm and the arithmetic, is a well-understood engineering task with directly measurable value in the model the laboratory operates, and it prepares the next rung, because a routine with an explicit interface and contiguous data can be replaced by a kernel.

Rung 4 addresses the question the laboratory asks: whether an H100 GPU can accelerate the model in operation. Upstream WW3 has no GPU execution path [@ww3repo]. The published port on record moved the source terms to the GPU with OpenACC directives and obtained roughly 1.3 times speed-up per node, limited by CPU–GPU traffic at every time step [@ikuyajolu2023]. By contrast, WAM6-GPU, the GPU version of another third-generation wave model, refactored the whole model to keep the fields in GPU memory and reported an order-of-magnitude gain on a multi-GPU node [@yuan2024]. The two results indicate that moving only part of the computation to the GPU, through directives and with the state on the CPU, gains little, and that the gain comes from kernels designed for the GPU. This project takes the intermediate path demonstrated by Koldunov et al. [-@koldunov2026], a preprint, for FESOM2: some 74 thousand lines of Fortran moved to C and then to C++/Kokkos in weeks, with an expert-directed LLM coding assistant, two-stage literal translation and a validation ladder. A kernel rewritten this way runs on CPU and on GPU from the same source, because Kokkos compiles that source to each machine's backend [@trott2022], and can be validated in isolation against the original Fortran. The criterion for entering operation is the same as for the other rungs: measured gain and no regression.

**State of WW3 testing.** The proposed validation rests on the model's own test infrastructure, surveyed at revision `develop` 7.14 in September 2026 [@ww3repo]. WW3 has 62 regression cases in `regtests/`, run by a matrix of scripts that compile switch combinations and compare the outputs of two runs file by file with `cmp` and `diff`, classifying each case as identical or not identical; the matrix includes variants for bit-for-bit reproducibility across restarts, thread counts and process counts. There is no tolerance-based comparison: any numerical difference is reported as a failure, and it falls to the reviewer to judge it. Unit tests have existed since 2023 but cover input and output only (five programs via CTest). Public continuous integration compiles with GNU and Intel and runs a single regression case; the full matrix runs on NCEP machines. For this project that defines the method: rungs 1 and 2 are validated with the model's own matrix, whose bit-for-bit criterion is the right one; rungs 3 and 4 require a per-field comparator with tolerances and per-routine unit tests, which WW3 does not have and which this project builds and delivers.

**State of WW4.** The WAVEWATCH IV repository was created in November 2025 and, on 15 September 2026, had 36 commits on `develop` and no published release [@ww4repo]. Phase II of the project (languages, governance and architecture) was completed in March 2026 [@on528]; the current code is a C++ core with utilities and a standalone executable, still without physics. The test strategy defines four levels, unit (L1), integration (L2), functional (L3) and regression (L4), in GoogleTest with CTest; L1 and L2 cover the existing code, while L3 and L4, which would replace the WW3 regression matrix, do not yet exist. The CPU–GPU architecture is an open question, with Kokkos named as the data abstraction layer. The first public release is expected in January 2027, and NOAA's plan only sunsets WW3 support once WW4 matures [@on525]. Two consequences follow: WW3 will remain the laboratory's operational model for years, which justifies optimising it; and the kernels rewritten here, with Kokkos and L1/L2 tests in the WW4 style, can inform the WW4 architecture discussion rather than duplicate it.
