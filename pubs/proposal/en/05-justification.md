# JUSTIFICATION

An operational forecasting chain is only as useful as its timeliness. For the wave field that feeds the ReNOMO products, a shorter cycle means earlier delivery, room for higher resolution at the same deadline, and the possibility of running several members to quantify uncertainty — the three axes NCEP tunes in its own operational system and which, there as here, are bounded by run time [@emcwaves; @campos2020]. WW3 was designed for the supercomputers of the last two decades and carries choices, in its build system, its data layout and its parallel decomposition, that are not automatically the best ones for today's machines: multi-core nodes with large memory, fast NVMe storage and, increasingly, GPUs.

The first two rungs are justified by the model's own documentation: the switch file and the compiler options decide which code is compiled and how, and the parallel layout decides how much time is spent moving spectra between processes rather than computing them [@ww3manual]. They are cheap rungs, frequently neglected in installations configured once and never revisited, and they produce the instrument the later rungs depend on: a reproducible benchmark and a profile. That is why they come first: no rewrite is justifiable before knowing how much of the run time survives them.

The third rung is justified by the structure of the code. Published profiling of WW3 shows that the source-term integration dominates the run time, with propagation second, and that the routines involved use large local arrays and module-level global state, which hinders both vectorisation and any form of offloading [@ikuyajolu2023]. Rewriting them in modern Fortran, preserving the algorithm and the arithmetic, is a well-understood engineering task with directly measurable value in the model the laboratory operates, and it prepares the next rung, because a routine with an explicit interface and contiguous data can be replaced by a kernel.

The fourth rung addresses the question the laboratory actually asks, whether an H100 can accelerate the model in operation. Upstream WW3 has no GPU execution path [@ww3repo]. The published port on record moved the source terms to the GPU with OpenACC directives and obtained roughly 1.3 times speed-up per node, limited by host–device traffic at every time step [@ikuyajolu2023]. By contrast, WAM6-GPU, which refactored the whole model to keep the fields resident on the device, reported an order-of-magnitude gain on a multi-GPU node [@yuan2024]. The lesson is that partial directive-based offloading with the state on the host does not pay, and that the gain comes from kernels designed for the device. This project takes the intermediate path demonstrated for FESOM2 by Koldunov et al. [-@koldunov2026], a preprint, who moved some 74 thousand lines of Fortran to C and then to C++/Kokkos in weeks, with an expert-directed LLM coding assistant, two-stage literal translation and a validation ladder. A kernel rewritten this way runs on CPU and on GPU from the same source, because Kokkos compiles that source to each machine's backend [@trott2022], and can be validated in isolation against the original Fortran. The criterion for entering operation is the same as for the other rungs, measured gain and no regression, not a decision taken in advance.

**State of WW3 testing.** The proposed validation rests on the model's own test infrastructure, surveyed at revision `develop` 7.14 in September 2026 [@ww3repo]. WW3 has 62 regression cases in `regtests/`, run by a matrix of scripts that compile switch combinations and compare the outputs of two runs file by file with `cmp` and `diff`, classifying each case as identical or not identical; the matrix includes specific variants for bit-for-bit reproducibility across restarts, thread counts and process counts. There is no tolerance-based comparison: any numerical difference is reported as a failure and it falls to the reviewer to judge it. Unit tests have existed since 2023 but cover input and output only (five programs via CTest). Public continuous integration compiles with GNU and Intel and runs a single regression case; the full matrix runs on NCEP machines. Recent activity concentrates on cleaning compiler warnings and fixing CI, with intermittent matrix failures open. For this project that defines the method: rungs 1 and 2 are validated with the model's own matrix, whose bit-for-bit criterion is the right one; rungs 3 and 4 require a per-field comparator with tolerances and per-routine unit tests, which WW3 does not have and which this project builds and delivers.

**State of WW4.** The WAVEWATCH IV repository was created in November 2025 and, on 15 September 2026, has 36 commits on `develop`, no published release and its last push in August 2026 [@ww4repo]. Phase II of the project (languages, governance and architecture) was completed in March 2026 [@on528]; the current code is a C++ core with utilities and a standalone executable, still without physics. The test strategy is defined at four levels — unit (L1), integration (L2), functional (L3) and regression (L4) — in GoogleTest with CTest, running in CI on every push; L1 and L2 were rewritten in July 2026 to cover all existing code, while L3 and L4, which would replace the WW3 regression matrix, do not yet exist. The build system is being simplified to pure CMake, and the CPU–GPU architecture is an open question, with Kokkos named as the data abstraction layer and the choice between one or two code bases still to be made. The first public release is expected in January 2027, and NOAA's plan only sunsets WW3 support once WW4 matures [@on525]. Two consequences follow: WW3 will remain the laboratory's operational model for years, which justifies optimising it; and the kernels rewritten here, with Kokkos and L1/L2 tests in the WW4 style, can inform the WW4 architecture discussion rather than duplicate it.
