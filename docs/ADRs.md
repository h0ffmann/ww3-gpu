# Architecture Decision Records

A decision record states one choice the lab has made, the context that forced it, the
alternatives weighed and what follows from it. It is shorter than a plan and it does not schedule
work: a WFIP ([`WFIPs/`](WFIPs/README.md)) designs a change and carries its definition of done,
while an ADR records a decision that several WFIPs and plans then follow.

Every ADR is a section of this one document ([ADR-0022](#adr-0022)), in the order of its number.
A section opens with `<a id="adr-NNNN"></a>`, so a link to it is `docs/ADRs.md#adr-NNNN`, then the
heading `## ADR-NNNN: <the decision>`, a header table (Status, Date, Deciders, Written by, Scope,
Related) and the subsections *Context*, *Decision*, *Alternatives considered*, *Consequences* and
*Revisit when*. A short ADR, such as one the `adr-verbatim` skill records from the owner's words,
may carry only Status, Date and the decision. Statuses: Proposed → Accepted, or Rejected, or
Superseded by ADR-NNNN. An accepted ADR is not edited; a new one supersedes it, and only the older
one's Status changes. The evidence rule of `CONTRIBUTING.md` applies: `(v)` with what was checked,
`⚠` when it was not. When the first change an ADR governs has landed, a *Results* subsection before
*Revisit when* records what it measured, each number with its command.

`just adrs` (or `/adrs` in Claude Code) prints one line per record: number, status, date and the
decision its heading states, read from the sections rather than from the table below. The same
reader fills the `/adrs/` page of the website on every build.

## ADR-0001: No proof language for the GPU port; SMT queries and exhaustive sweeps instead

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 |
| **Deciders** | Hoffmann |
| **Written by** | Hoffmann, with an agent |
| **Scope** | Every route that moves WW3 work off the Fortran CPU path: the C++/Kokkos port, the Triton arms of `W3SDS4`, and the WeatherNext 3 wind forcing |
| **Related** | [`BITWISE_PROOF_202610.md`](BITWISE_PROOF_202610.md) (the evidence), [`docs/proof/`](proof/README.md) (one page per tool), [#45](https://github.com/h0ffmann/ww3-gpu/issues/45) and [`W3SDS4_TRITON_PLANO_202610.pt.md`](W3SDS4_TRITON_PLANO_202610.pt.md) (Triton), [WFIP-0001](WFIPs/WFIP-0001-weathernext3-wind-rtx4090.md) (WeatherNext 3), #58 (Bend removed) |

### Context

The lab's claim is that WW3's expensive kernels can move to a GPU "without changing the answer".
The project proposal states that claim in two strengths. Options that leave the arithmetic alone
must reproduce the reference "bit a bit, arquivo a arquivo", and the Kokkos Serial backend must
reproduce the C reference bit for bit `(v, pubs/proposal/pt/07-methodology.md:14, :16)`.
Everything else is judged by tolerances agreed with the laboratory
`(v, pubs/proposal/pt/06-objective.md:4)`.

Today the strong claim rests on tests. `W3SNL1` is bit-identical to the Fortran on the Serial,
OpenMP and CUDA presets on the three fixture points `(v, kokkos/PORT_STATUS.md:13)`. Section 1 of
that kernel was also swept over all 2^32 float32 inputs with 0 differences at the parity flags
(`bash proof/snl1_cons/run.sh`, `BITWISE_PROOF` §4). The question is whether to go further and
adopt a proof language (Rocq, Lean 4, Isabelle, Agda, Idris 2, Liquid Haskell, TLA+, F\*, or the
since-removed Bend) as part of the port's workflow.

Four facts shape the answer:

1. **No proof assistant reads Fortran or C++.** Each one proves theorems about a model written by
   hand. Only Rocq reaches real C code, through CompCert's Clight and VST, and it does not reach
   C++ or Fortran `(v, BITWISE_PROOF §6)`. A proof about a hand-written model says nothing about
   the gfortran and nvcc binaries the lab runs unless someone shows that the model and the code
   agree, and that link is exactly what is in question.
2. **Bit equality is a property of two binaries, not of two sources.** The same three Fortran
   lines give different bits under `-O3` and under `-O3 -march=x86-64-v3` (FMA). A Kokkos build
   without `-ffp-contract=off` differs on 4 632 147 inputs of section 1 `(v, BITWISE_PROOF §4)`.
   A useful proof has to be tied to the flags it was taken with.
3. **IEEE-754 arithmetic is decidable for straight-line code.** SMT-LIB's `QF_FP` theory models
   binary32 and binary64 exactly, with rounding modes, ±0, NaN and FMA. Bitwuzla and cvc5 answered
   both pilot queries in 0.4–79 s, while Z3 did not finish one `unsat` in 15 min
   `(v, BITWISE_PROOF §3(c))`. For a loop body, equality "for every input" is therefore a solver
   query, not a proof someone has to write.
4. **A proof language multiplies what agents write and people review.** In this lab an agent
   writes most of the code and a person reviews all of it. A proof assistant adds a second artefact
   per routine: the hand-written model, its lemmas and the proof scripts, which have to be kept in
   step with the C++ and re-checked when it changes. Each of those is more tokens generated and
   more lines a reviewer must read, and the reviewer must also check that the model says what the
   code does, which Appendix A shows a checker cannot do. `BITWISE_PROOF` rates interactive proofs
   at months per routine against 1–3 days per loop body for an SMT query
   `(v, BITWISE_PROOF §7)`. The token and review cost of either route has not
   been measured ⚠; the claim is that it scales with the size of the formal artefact, which is a
   solver query for SMT and a whole theory for a proof assistant.

### Decision

**No proof assistant or dependently typed language is adopted.** Bit-for-bit claims are
established by three mechanised checks that read either the binaries or the operation DAG:

1. **Exhaustive sweeps.** Every function of one float32 input and every integer table (DIA
   addresses, `ISP` maps, `MAPSTA`) is swept over all of its inputs, comparing the Fortran build
   against the port build at the parity flags.
2. **GIMPLE diff.** gfortran and g++ share GCC's middle end, so the optimised IR of each routine is
   normalised and diffed. This shows the same floating-point operations in the same order.
3. **SMT-LIB `QF_FP` queries, decided by Bitwuzla or cvc5.** Each loop body is written as the
   Fortran DAG against the C++ DAG. Every rewrite an agent proposes gets one query too, and the
   answer must be `unsat` before the rewrite is merged.

SMT-LIB is the only formal language adopted. It is used as a query format checked by a decision
procedure, so nobody writes or maintains a proof script. Three tools stay on the bench for later
and are not adopted now:
- ESBMC builds the SMT queries from the C++ and CUDA sources itself.
- TLA+ can specify the phase-3 halo exchange and a fixed reduction schedule, which are protocol
  questions rather than arithmetic.
- VCFloat2, which runs on Rocq, can prove a round-off bound when a tolerance has to be defended in
  a paper.

### The decision per scenario

| Scenario | What "the same answer" means here | Bit-for-bit reachable? | What establishes it | Proof language? |
|---|---|---|---|---|
| **Kokkos/C++ on CPU** (Serial, OpenMP; `W3SNL1` now, `W3SDS4` next) | identical bits to gfortran at WW3's GNU flags | **Yes, provably**, for kernels without a reduction, with contraction off on both sides and the same libm entry points `(v, BITWISE_PROOF §2)` | sweeps, GIMPLE diff, SMT per loop body; L1 and L2 tests stay as the regression net | No |
| **Kokkos with reductions** (`W3SRCE`, ST4 integrals by `team_reduce`) | a fixed-order validation build equal to the Fortran; production within tolerance | **No** against a parallel reduction, by construction. Float addition is not associative. | `WW_DETERMINISTIC=ON` for validation (fixed order, then provable as above); `nccmp-tol` per field for production | No; TLA+ later for the reduction schedule, if phase 3 needs one |
| **Kokkos on CUDA** (RTX 4090, H100) | as on CPU for `+ − × ÷ sqrt` with `--fmad=false`; tolerance once a transcendental appears | **Partly.** CUDA's `expf` is another implementation (about 2 ULP ⚠), so only the routines with no transcendental are provable. | an exhaustive count of where device and glibc libm disagree on each routine's real input domain, then `nccmp-tol` | No; a VCFloat2 bound only if a reviewer asks why the tolerance is what it is |
| **Triton `W3SDS4`** (GPU, and `triton-cpu` as a parity twin) | the L1 tolerance gate, as for Kokkos | **Improbable** `(v, W3SDS4_TRITON_PLANO, "Resumo", item 4)`: `libdevice` transcendentals, FMA fusion by default, reduction order, and TF32 in `tl.dot` | the plan's own gates: `enable_fp_fusion=False`, `input_precision="ieee"`, ULP tests of `exp`/`log`/`tanh`/`atan2` against glibc, L1 and L2. SMT can still prove that a kernel's written DAG equals the Fortran's for the arithmetic-only parts. Triton lowers through MLIR and LLVM, so there is no GIMPLE diff; Alive2 on the LLVM IR is the only IR-level option ⚠ (not tried). | No |
| **WeatherNext 3 wind forcing** (WFIP-0001) | not the same answer: a different wind field gives a different `Hs` by design | **Not applicable** | a statistical comparison: bias and RMSE of `Hs` against PNBOIA buoys or altimeter tracks, against the GFS/IFS-driven run `(v, WFIP-0001 §7)`. The forcing pipeline (regrid, units, time interpolation) is checked by tests on known fields. | No. A proof cannot say whether one wind model forecasts better than another. |

Across the five rows, a proof language would only add something for theorems about a model of the
physics (energy conservation of the DIA quadruplet, positivity of a limiter). Those are true in
real arithmetic and generally false bit for bit in float32, so they stay as the L1 property tests
`kokkos/tests/` already runs (zero in, zero out; `A×2 → S×8`) `(v, BITWISE_PROOF §3(b))`.

### Alternatives considered

| Option | Why not now | Page |
|---|---|---|
| Rocq + Flocq (CompCert, VST) | It is the reference IEEE-754 theory and the only one that reaches real C, but it reaches no C++, Fortran, CUDA or Triton. The proofs take months for one routine and are written by hand. CompCert's licence is non-commercial. | [rocq-flocq](proof/rocq-flocq.md) |
| Lean 4 (+ FloatSpec) | Core Lean now has a bit-level model of `+ − × ÷`, but `exp` is still `opaque` `(v, lean4 Init/Data/Float)`, and Lean has no path to C++. A Lean check of an agent-written model is only as faithful as that translation (Appendix A). | [lean4](proof/lean4.md) |
| Isabelle/HOL | The AFP `IEEE_Floating_Point` entry includes FMA, but Isabelle has no C or C++ front end. | [isabelle-hol](proof/isabelle-hol.md) |
| Agda, Idris 2 | `Float` is a postulate, so nothing can be proved about bits. | [agda-idris2](proof/agda-idris2.md) |
| Liquid Haskell | It reads `Double` as an SMT real, which is unsound for bits. | [haskell-liquid-quickcheck](proof/haskell-liquid-quickcheck.md) |
| TLA+ | It is the right tool for protocols and reductions, not for arithmetic. It is deferred to phase 3, not rejected. | [tla-plus](proof/tla-plus.md) |
| F\* | Its verified code (HACL\*, Low\*) is integer and cryptographic, with nothing for floating point ⚠. | `BITWISE_PROOF` §6 |
| Bend | Its `F32` operations are axioms in its checker and it has no F64; it was removed from the repository in #58. | — |
| ESBMC, CBMC, Alive2 | These are not rejected. They are the next rung of the ladder, and they are tools rather than languages. | [cbmc-esbmc](proof/cbmc-esbmc.md), [alive2](proof/alive2.md) |

### Consequences

- **Nothing new to learn or install for the port.** The solvers are installed by the user with
  `pip install bitwuzla cvc5` and are never vendored. The sweeps and the GIMPLE diff use the
  gfortran and g++ the toolchain already pins.
- **Proofs are tied to a build.** A change of compiler, flags or libm means re-running the sweeps
  and the queries, so they belong in CI next to the L1 tests, not in a document. A proof result
  enters `kokkos/PORT_STATUS.md` as a "proved / tested" column (`BITWISE_PROOF` §4 step 6).
- **The queries are written by hand until ESBMC takes over.** That costs 1–3 days per loop body
  `(v, BITWISE_PROOF §7)`, which is affordable for the DIA and for `W3SDS4` and not for all of
  `W3SRCE`.
- **No theorem about the physics.** Conservation and sign properties stay as tests. This record
  makes no claim that the port is physically correct beyond agreeing with the Fortran.
- **Triton and WeatherNext 3 carry no bit-for-bit claim.** Their gates are tolerances and skill
  scores, and their write-ups must not borrow the Kokkos port's "bit-identical" label.

### Revisit when

- Lean 4 gains an `exp` model or a verified path to C or C++.
- A tolerance (the CUDA one, the Triton one, or ST4's reductions) has to be defended in a
  publication. Then a VCFloat2 or Gappa bound becomes worth its cost.
- Triton gains a documented bitwise-reproducible mode ⚠ (none known on 2026-10-08).
- NOAA-EMC/WW4 adopts a formal method for its own GPU port (`just ww4-status` would show it).

### Appendix A: evidence from autoformalisation

Bastounis, Circelli and Hansen (2026), *Navier-Stokes lost in translation: Why Lean verification
of AI autoformalisation does not guarantee correct natural language proofs*,
[arXiv:2610.08144](https://arxiv.org/abs/2610.08144) `(v, read on arxiv.org on 2026-10-09)`.

The paper studies proofs that an AI translates from prose into Lean and then has Lean check. Its
thesis is that "Lean acceptance (compilation) of translation does not imply semantic
preservation" (§4.3). §2 gives translations that turn a wrong proof into a correct Lean proof. §3
argues that the Lean code published with OpenAI's Navier-Stokes blow-up claim states weaker
results than the paper it was translated from. §4 argues that resolving the ambiguities of a text
is not computable in general (it sits at the top of the Solvability Complexity Index hierarchy).

This supports fact 1 of the context by analogy. A checked theorem is a statement about the
formal model, and its value depends on a translation step the checker does not see. Here that step
is from the gfortran and nvcc builds to a hand-written model; in the paper it is from prose to
Lean. The paper also covers the case of an agent writing the model, which is how a proof
language would enter this repository.

Its limits for this record:
- It is about mathematics translated from prose, not about code. It says nothing about floating
  point, compilers or GPUs.
- It gives worked examples and a complexity argument, not error rates.
- It does not bear on the SMT route of the decision, whose queries are written from the Fortran
  and C++ operation graphs rather than from prose. A hand-written query carries the same fidelity
  risk in a smaller form, which is why ESBMC, which builds the queries from the sources, is the
  next rung.

## ADR-0002: Port order is measured wall time, most expensive first

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 |
| **Deciders** | Hoffmann |
| **Written by** | Hoffmann, with an agent |
| **Scope** | The order in which WW3 routines are ported off the Fortran CPU path, by any route: the C++/Kokkos port, the Triton arms, and any later experiment arm |
| **Related** | [`CONTRIBUTING.md`, "Port order is wall time"](../CONTRIBUTING.md#port-order-is-wall-time) (the rule), [`AGENTS.md`, "Porting"](../AGENTS.md#porting-hard-rule), [`AGENTS_KOKKOS_202609.md` §2.2](AGENTS_KOKKOS_202609.md#22-ranked-port-list), [`ww3_ts1_gprof_202610.md`](data/ww3_ts1_gprof_202610.md) (the first measurement), #46 and #69 (the change), #42 (port planner), #45 (`W3SDS4`) |

### Context

Before this decision, `AGENTS_KOKKOS` §2.2 ranked routines by one score:
(runtime share) × (Kokkos suitability) × (ensemble-batching payoff) ÷ (engineering effort +
validation risk). The score let a routine that is cheap to validate, already has a fixture, or maps
well to a GPU move ahead of one that costs more wall time. The point of the port is to cut the
wall-clock time of the forecast `(v, docs/AGENTS_KOKKOS_202609.md:5)`, so porting a cheap routine
first spends effort where it buys little.

The shares behind the score were priors, not measurements: the §2.1 table gives ranges such as
40–65 % for the source terms, taken from published profiling of WW3 6.07 on Summit (Ikuyajolu et
al., GMD 2023), and marks them as priors to confirm `(v, docs/AGENTS_KOKKOS_202609.md:164)`.

The first measurement in this repository already disagrees with the prior order. In `regtests/ww3_ts1`
at `WW3@761cf79d` with `switch_lab_shrd` (ST4, NL1), gprof attributes 2.01 s of the 2.98 s of
source-term self time to `W3SDS4` and 0.42 s to `W3SNL1`; with `SDSCUM=0` the figures are 0.51 s
and 0.45 s of 1.33 s `(v, docs/data/ww3_ts1_gprof_202610.md)`. That table is ⚠: transcribed from
#45 and not yet reproduced by a committed command. §2.2 had `W3SNL1` first.

`AGENTS.md` already stated the rule ("Order follows wall time", the rule of #46) while §2.2 and
lesson 13 still used the score, so the repository contradicted itself until #69.

### Decision

**Routines are ported in descending order of the wall-clock time they take in the operational
case, most expensive first. Nothing else sets the order.**

1. The measurement is the phase-0 profile (`AGENTS_KOKKOS` §2.4, task P0.1 of #42): inclusive and
   exclusive wall time per routine on 1, 4 and 16 ranks, committed with the command that produced
   it.
2. Until that profile is committed, the order follows the best evidence there is, marked `⚠`: the
   `ww3_ts1` gprof table inside the source terms, and the §2.1 priors outside them. The queue is
   re-sorted the day the profile lands.
3. A routine that cannot start because of a dependency keeps its place, and the next one down
   starts meanwhile. `W3SRCE` is the case: counted inclusively it is the most expensive source-term routine,
   because it calls the source terms, but its device version needs those source terms first, so
   `W3SDS4` and `W3SIN4` go before it.
4. Effort, Kokkos suitability and ensemble payoff stay in the §2.2 table to plan each task. They do
   not change the order.
5. Experiment arms (Triton, #45) follow the same rule: they target the routine at the top of the
   ranking, not the one that is cheapest to try.

### Alternatives considered

| Option | Why not |
|---|---|
| Keep the §2.2 score | It mixes cost with convenience, and its runtime factor was a prior. It ranked `W3SNL1` above `W3SDS4`, which the first measurement contradicts. |
| Easiest to validate first | It builds tests and fixtures quickly but spends the port's effort where the wall time is not. `W3SNL1` was ported first on these grounds; that is history, not a precedent. |
| Best GPU fit first | A good GPU kernel for a routine that takes little time does not move the forecast's wall time, and phase 1 copies per call, so the transfer cost can exceed the saving. |
| Wait for the full profile before porting anything | It stalls the work. The gprof table and the priors are enough to pick the next routine, provided they are marked `⚠` and the order is re-sorted when the profile lands. |

### Consequences

- **`W3SDS4` is the next port after `W3SNL1`**, before `W3SIN4` `(v, AGENTS.md:158)`.
- **The profile becomes a gate, not a nice-to-have.** Every re-sort of the queue points at a
  committed profile and its command; a port proposal that skips the top of the ranking has to say
  which dependency blocks it.
- **The ranking can change under a running task.** A task already started is finished; the next
  pick follows the new order.
- **Wall time on which machine.** The ranking is taken on the operational case and the CPU build;
  a routine that is cheap on CPU and expensive once the rest is on the GPU (a transfer, a
  gather/scatter) re-enters through the next profile, not through a guess.

### Revisit when

- The phase-0 profile (#42, P0.1) lands and contradicts the `ww3_ts1` order.
- The operational case changes (a new grid, physics switch or ensemble size), since the ranking is
  per case.
- After phase 2, when the spectrum stays on the device and the cost that matters is the remaining
  CPU work plus transfers, not the CPU profile.

| **Related** | [WFIP-0002](WFIPs/WFIP-0002-lab-as-a-book.md) (the plan that builds the book); marola's [MIP-0014](https://github.com/marola-dev/marola/blob/main/docs/MIPs/MIP-0014-marola-book.md) (the design it is translated from); [`CONTRIBUTING.md`, "Who this repository is for"](../CONTRIBUTING.md#who-this-repository-is-for); the `release` skill; [`pubs/README.md`](../pubs/README.md) |

### Context

The repository started as a lab: a course on running WW3, a pinned toolchain, a Kokkos port of one
kernel, benchmarks, plans and a project proposal `(v)` [`README.md`](../README.md) at
`main@5a4f3bf`. Along the way it acquired a method that is now its most distinctive content: coding
agents port Fortran under a bit-for-bit gate and a validation ladder (`AGENTS_KOKKOS`, lesson 13);
every claim carries `(v)` or `⚠` and every number its command; a change is designed as a WFIP with a
definition of done before it is built; a decision is an ADR; what was tried goes in a dated log;
releases carry the WFIP status into Zenodo `(v)` [`AGENTS.md`](../AGENTS.md), read 2026-10-08.

That method is spread over `AGENTS.md`, two plans, five skills, the WFIP template and sixteen
lessons. A reader who wants it has to assemble it. The lessons already compile into a PDF on every

form exists and only the framing is missing. marola's MIP-0014 found the same gap in its own
repository and proposed a self-published technical book built from the repository, in the tradition
of Sandy Maguire's and Gabriel Volpe's books `(v)` MIP-0014 §1–§4, read 2026-10-08 (the books
themselves were fetched by that MIP on 2026-09-05, not here ⚠).

### Decision

**The repository is a book in progress, compiled from the repository, on agentic coding and agentic
research applied to one problem: moving WW3's kernels to GPUs without changing the answer.**

1. The lessons in `course/` are the book's chapters, grouped in parts; the rules the lab runs by
   become chapters of their own (WFIP-0002 §5.2). Code, plans, measurements and the proposal stay
   where they are and keep their rules; they are the book's evidence, versioned with the text.
2. The README leads with the book. The repository keeps its name, `ww3-gpu`, and its title, WW3 GPU
   Lab; the book has a title of its own (WFIP-0002 §5.1, a person's choice).
3. Each tagged release is an edition: the PDF is attached to the release and archived with the
   source on Zenodo; the citation metadata (title, abstract, keywords) describes the book and its
   two audiences.
4. The shift is incremental. One PR per task of `WFIP-0002.tasks.md`; after each, the repository
   is consistent and every gate is green.
5. Nothing in `AGENTS.md` changes: WW3 read-only, translate don't improve, no timing without parity,
   the proposal through its reviewer, `Tested:`/`Cost:` on every commit. A chapter that contradicts
   `PORT_STATUS.md` is a bug in the chapter.

### Alternatives considered

| Option | Why not |
|---|---|
| Stay a lab, keep the course as a by-product | The method stays implicit and the second audience (people running agents on scientific code) never finds it; the PDF keeps a title the repository no longer has. |
| A separate book repository, as MIP-0014 §5.4 picked for marola | Right where the TeX closure would land on every contributor; here the publisher toolchain is already in the root flake and costs a contributor nothing, and the code the book cites is versioned next to the text. |
| Rename the repository to the book's title | Breaks every inbound link and the Zenodo and Software Heritage chain for a name; the book's title can live on the title page. |
| A book on wave modelling alone | The lessons already are one; what is new and scarce is the agentic method with its evidence, which is why it leads. |

### Consequences

- WFIP-0002 carries the work: parts and front matter, a listings gate, the PDF on each release,
  three new chapters, the metadata.
- The README, `DESCRIPTION.md`, `CITATION.cff`, `.zenodo.json` and `codemeta.json` describe a book
  from the next release on; the concept DOI does not change.
- The audience rule of `CONTRIBUTING.md` gains one sentence for the second reader and loses
  nothing: a chapter is wrong if a wave modeller reading over the shoulder finds a mistake.
- Every document in `docs/` is a chapter candidate, which raises the bar on its prose: `just vale`
  and `humanizer` apply to anything that may be compiled.
- A chapter that quotes a file is checked against that file in CI (WFIP-0002 §5.3), so a stale
  `file:line` fails the build instead of reaching a reader.

### Revisit when

- The first edition is cut (every box of WFIP-0002 §7 ticked) and a reader outside wave modelling
  has read it: does the framing hold?
- The proposal is defended (05/2027 in `08-schedule.md`): the book's Part V may become the report.

## ADR-0004: The book's channels: GitHub as the source, a PDF per release on Zenodo, a free Leanpub edition generated by CI

| | |
|---|---|
| **Status** | Superseded by [ADR-0023](#adr-0023) |
| **Date** | 2026-10-08 |
| **Deciders** | Hoffmann |
| **Written by** | Hoffmann, with an agent |
| **Scope** | Where a reader finds the book and how each edition is produced: the GitHub repository's public face, the PDF built on release, the Leanpub edition and what generates each. Not the book's content or title (ADR-0003, WFIP-0002 §5.1) |
| **Related** | [ADR-0003](#adr-0003) (the decision this one distributes); [WFIP-0002](WFIPs/WFIP-0002-lab-as-a-book.md) §5.5–§5.7 and task 4b; [`LEANPUB_202610.md`](https://github.com/h0ffmann/ww3-gpu/blob/f9ce3a0/docs/LEANPUB_202610.md) (the author's steps); [`pubs/README.md`](../pubs/README.md) (the PDF pipeline); the `release` skill; the repositioning PR [#74](https://github.com/h0ffmann/ww3-gpu/pull/74), whose results close this record |

### Context

ADR-0003 made the repository a book in progress. A book needs a place where readers find it and a
way for each edition to reach that place without a person assembling it. The repository already
had one channel: `pubs.yml` builds `pdf/ww3-lab-course.pdf` from `course/` on every merge and
commits it `(v)` [`pubs/README.md`](../pubs/README.md), read 2026-10-08. It had no public
framing on GitHub (description, topics and website were the lab's), no edition attached to a
release, and no edition outside the repository.

The owner asked for two more things on 2026-10-08: that the repositioning be made explicit in the
GitHub repository itself, and that the book be published free on Leanpub, with the publishing as
CI/CD, as soon as possible. Three facts, read on Leanpub's pages that day, bound the design:

1. Leanpub reads a `manuscript/` directory from a branch of a GitHub repository the author names,
   and never writes to the repository `(v)` [Getting started with the Git and GitHub writing
   mode](http://help.leanpub.com/en/articles/2916385-getting-started-using-leanpub-s-git-and-github-writing-mode-to-write-and-publish-a-book).
   Our lessons are GitHub-flavoured Markdown with Mermaid fences and `$…$` math; Leanpub reads
   Markua, which differs in math, part headings, asides and image paths `(v)`
   [Markua manual](https://leanpub.com/read/markua/headings).
2. Previewing and publishing through the API needs a Pro author membership `(v)`
   [leanpub.com/help/api](https://leanpub.com/help/api). Webhooks on a push trigger a preview or a
   publish without the API, and their payload URLs carry the author's key `(v)`
   [Setting up webhooks](http://help.leanpub.com/en/articles/5243991-setting-up-webhooks-if-you-re-using-leanpub-s-github-writing-mode-for-your-book).
3. "Free" is the reader's price, not the author's: the minimum price can be 0 `(v)`
   [Author Manual, Pricing](https://leanpub.com/help/manual), and a new book costs its author a
   one-time 99 USD, "even free" and in every writing mode, unless the account is grandfathered
   `(v)` [leanpub.com/pricing](https://leanpub.com/pricing).

Repository settings (description, website, topics) cannot be written from the agent's session: the
GitHub proxy answers `403 Repository settings writes are not permitted through this proxy`
`(v)` session of 2026-10-08. Creating a Leanpub book needs the author's account.

### Decision

**The book has four channels, each produced by CI from `course/` on `main`, and the repository is
described as the book on GitHub.**

1. **GitHub is the source and the first page.** The README leads with the book; the repository's
   description, website (the concept DOI) and topics describe a book on agentic coding and agentic
   research around a GPU port of WW3. The 20 topics and the description text are fixed in WFIP-0002
   §5.6 and in PR #74; setting them is the owner's act, since the proxy refuses it.
2. **The PDF is the edition of record.** `pubs.yml` keeps building it on every merge; WFIP-0002
   task 4 attaches it to each tagged release, where Zenodo archives it with the source under the
   concept DOI `10.5281/zenodo.23221351`.
3. **Leanpub is the free reading edition, generated and never edited.** `scripts/leanpub_manuscript.py`
   exports the lessons as a Markua manuscript (parts from `pubs/book/parts.json`, figure renders as
   images, reading cards as asides, math and links converted) and `.github/workflows/leanpub.yml`
   force-pushes it as the single commit of the `leanpub` branch on every merge that touches a
   lesson and on every release. The book on Leanpub points at that branch for previews and
   publishing. With the `LEANPUB_API_KEY` secret the workflow previews and publishes through the
   API; without it, a webhook or a click on leanpub.com does, so the pipeline does not depend on a
   paid plan.
4. **The reader pays nothing.** Minimum price 0 on Leanpub, the PDF free on the release and Zenodo.
   The author pays Leanpub's one-time fee per new book unless grandfathered; the repository takes
   no position on a suggested price.
5. **A chapter is fixed in `course/`, never in a generated edition.** The `leanpub` branch and
   `pdf/` are outputs; a `⚠` is as visible on Leanpub as on GitHub, by design.
6. **The website is the reading edition on the open web** (added 2026-10-08, issue #76).
   `scripts/build_html.sh` builds `course/` into one page per chapter with pandoc's `chunkedhtml`
   writer, the same reader and figure filter as the PDF, and MathML for the math, so the site
   loads nothing from a CDN; `.github/workflows/pages.yml` builds it on every pull request that
   touches a lesson and deploys it to <https://h0ffmann.github.io/ww3-gpu/> on every merge and
   release. Like the `leanpub` branch, it is an output and is never edited.

### Alternatives considered

| Option | Why not |
|---|---|
| Commit `manuscript/` on `main`, as Leanpub's guide assumes | Doubles every lesson in the tree and invites edits to a generated file; the orphan `leanpub` branch keeps `main` as the only source and costs one force-push per merge. |
| Upload the PDF to Leanpub ("Upload" writing mode) | Leanpub's PDF is built from the manuscript, with its own sample, EPUB and reader updates; uploading our PDF loses them and still needs a person per edition. |
| API only, from CI | Needs a Pro membership for every preview; the branch push plus webhook gives the same automation at no plan. The API path stays as an option behind a secret. |
| Pandoc to Markua instead of a small exporter | Pandoc has a Markua writer `(v)` `pandoc --list-output-formats`, pandoc 3.1.3, 2026-10-08, but it converts one file's syntax, not the book: parts from `parts.json`, lesson links to chapter links, repository links to GitHub URLs, reading cards to asides, `Book.txt` and `Sample.txt` still need a script, and that script's five syntax conversions are smaller than a pandoc dependency in the CI job. Not rejected for later, if Markua's grammar outgrows the script. |
| A paid Leanpub book, or a reader price above 0 | The owner asked for free; the proposal's audience includes students; the PDF is free already, so a price would only move readers. |
| mdBook, MkDocs or Jekyll for the website | Each adds a second Markdown dialect or a plugin set to keep green, and none applies `mermaid.lua` or `book_prep.py`; pandoc already builds the PDF and Word files from the same inputs. Jekyll, GitHub's default, renders neither the math nor the figures. Compared in issue #76. |

### Consequences

- `course/` is now the source of three outputs, so every lesson change is gated three times:
  `pubs.yml` (PDF), `ci.yml` (the Markua export must succeed) and `leanpub.yml` (the push).
- Every merge to `main` that touches a lesson, a figure render or `parts.json` rewrites the
  `leanpub` branch. Nothing may be committed to that branch by hand; it is deleted and regenerated
  without notice.
- Two secrets may enter the repository, both optional: `LEANPUB_API_KEY` (Pro) and the webhook
  payload URL (which embeds the key). Neither is required for the pipeline to run.
- The author owns four steps the repository cannot do: set the GitHub description, website and
  topics; create the Leanpub book pointing at `h0ffmann/ww3-gpu` branch `leanpub`; add the
  `leanpub` GitHub user as a collaborator; run the workflow once ([`LEANPUB_202610.md`](https://github.com/h0ffmann/ww3-gpu/blob/f9ce3a0/docs/LEANPUB_202610.md),
  "Steps for the author").
- The Markua part syntax is in transition (`# Part #` today, `{class: part}` announced `(v)`
  Markua headings); the exporter writes the announced form and the doc names the one-line fallback.

## ADR-0005: The Claude project's settings are snapshotted in the repository, dated, except memory, connectors and secrets

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-09 |
| **Deciders** | Hoffmann |
| **Written by** | Hoffmann, with an agent |
| **Scope** | The settings of the Claude project "Wave Forecaster" that live on the Claude service: instructions, repositories, session defaults, the cloud environment, routines, memory, connectors. Not the Claude Code configuration already in `.claude/` and `AGENTS.md`, which is in git by construction |
| **Related** | [`.claude/project/`](../.claude/project/README.md) (the snapshot); [lesson 19](https://github.com/h0ffmann/ww3-gpu/blob/f9ce3a0/course/19-two-agents-one-issue-tracker.md) (the A2A routine and the trap that its prompt is not in git); [`AGENTS.md`, "Messages between Claude projects"](../AGENTS.md#messages-between-claude-projects); [ADR-0003](#adr-0003) (the book, whose subject is the method these settings encode) |

### Context

The agents that work on this repository run in two layers. The first is Claude Code's own
configuration, and it is already in git: hooks and permissions in `.claude/settings.json`, the
skills, the `revisor-proposta` agent, the slash commands, `AGENTS.md` and `CLAUDE.md` `(v)`
`ls .claude/`, 2026-10-09. The second is the Claude project the owner works in, whose settings
are stored on the service and reach a session only through it: the project instructions, the
repositories attached, the model and effort of thread sessions, the cloud environment, the
routines, the project memory and the connectors.

The second layer changes behaviour as much as the first, and nothing records it. Lesson 19 found
this the hard way: the A2A routine's prompt is the receiver's whole program, it lives on the
service, and the lesson's quoted copy goes stale silently when the prompt is edited there
`(v)` [lesson 19](https://github.com/h0ffmann/ww3-gpu/blob/f9ce3a0/course/19-two-agents-one-issue-tracker.md), "The receiver is a routine".
A reader of the book who wants to reproduce the setup cannot see that layer, and neither can a
reviewer of a PR that depends on it. The owner asked on 2026-10-09 whether all of it could be
kept in the repository for reproducibility.

What the project's sessions can read back, checked on 2026-10-09 `(v)` from a thread session and, for `get_project_settings`, from the coordinator session:

| Setting | Readable from a session | Exportable to git |
|---|---|---|
| Name, visibility, repositories | yes, in the session context | yes |
| Project instructions, default model, routine and task settings | yes, `get_project_settings` (coordinator session only); instructions are empty, no effort default is set | yes |
| Model, effort, permission mode of a session | yes, `get_session`, for that session | yes |
| Cloud environment | name, kind and network policy, `list_environments` | yes; its secrets and variables no |
| Routines | name, schedule, stored prompt, `list_triggers` / `get_trigger` | yes, prompt verbatim |
| Project memory | only through the coordinator's memory tools; on 2026-10-09 it was off in the owner's account settings, so empty | in part: content a person reviews, never wholesale |
| Connectors (Gmail, Calendar, Drive, Docs, GitHub) | names only; they belong to the owner's account | no: each is an OAuth sign-in |
| Chats, artifacts, project files | readable, and not settings | no |

The service also returns identifiers that must not be committed: the creator's account id on
each routine and the owner's e-mail address in the session context.

### Decision

**The project's settings are kept in `.claude/project/` as a dated snapshot that a person can
restore from by hand. The service stays the truth; the snapshot is its copy, read back with the
service's own tools and committed with the date it was read.**

1. `project.json` holds what the table marks exportable: name, visibility, instructions,
   repositories, default model, memory and routine settings, what a thread session runs with, environment name and network
   policy, and each routine's name, trigger id, schedule and the path of its prompt file. It
   carries `read_on` and the tools it was read with.
2. Each routine's prompt is a text file under `routines/`, verbatim. Lesson 19 keeps quoting it,
   and `tests/test_claude_project.py` fails if the lesson and the file differ, so the two copies in
   git cannot drift from each other.
3. Only the project's own routines go in. Routines on the same account that belong to another
   project (Marola Agent's inbox, its PR check-ins) stay out: they are that project's settings.
4. Memory, connectors, secrets, chats, artifacts and project files are listed under
   `not_in_this_snapshot` and stay out. A lesson learned in memory that should survive is promoted
   by a person into `AGENTS.md`, a skill or a doc, where review and the evidence rule apply.
5. No e-mail address, account id or credential is committed; the test above checks the folder for
   the first two patterns.
6. A change to the project on the service is followed by a PR that updates the snapshot and its
   `read_on`. No CI job can check the snapshot against the service, since no command outside a
   Claude session can read the project. A weekly routine of the project does it instead (added
   2026-10-09 at the owner's request): every Friday at 02:30 São Paulo time it re-reads the
   routines, the session defaults and the environment, opens a PR when anything changed and never
   merges. Its own prompt is in the snapshot, `routines/weekly-settings-snapshot.txt`. It cannot
   re-read the `project` block, since `get_project_settings` exists only in the coordinator
   session; that block stays a hand update, and the routine's PR says so.

### Alternatives considered

| Option | Why not |
|---|---|
| Keep nothing; the service is enough | A copy in a lesson goes stale with no signal (the routine's schedule was changed on the service the night it was created); a reader of the book cannot rebuild the setup. |
| Export everything, memory included, on a schedule | Memory is written by sessions and holds notes, partial findings and the owner's preferences; committing it unreviewed bypasses the evidence rule and risks personal data. The memory tools are also not available to every session. |
| Generate the snapshot with a script in CI | There is no API the repository can call: the project is reachable only from inside a Claude session, through its tools. A routine could write it, but a routine that pushes to the repository needs the owner's approval for each push anyway. |
| Put the snapshot in `docs/` | It is configuration for agents, next to the rest of it in `.claude/`; `docs/` holds what is argued, this holds what is set. |
| Make the snapshot authoritative and apply it to the service | The service has no import; restoring is a person following `.claude/project/README.md`. |

### Consequences

- The book's chapter on two agents (lesson 19) and its routine now point at one file in git, and a
  test ties them.
- A PR that edits a routine prompt shows the edit as a diff, which a reviewer can read; the edit on
  the service is still made by a person or a session of this project.
- The snapshot can be stale between a change on the service and the PR that records it; `read_on`
  says how old it is.
- The snapshot is complete only while memory stays off; if the owner turns it on, what it holds is
  read and triaged by the rule in point 4.

### Revisit when

- The service gains an export or import for projects, or an API a CI job can call: then the
  snapshot is generated and checked, and this record is superseded.
- The project gains instructions or a second environment.
- The snapshot routine's PRs keep reporting the `project` block as not re-read while it has changed.
- Memory turns out to hold settings the work depends on that no file in git carries.

| Graph `(v)` | 2,427 nodes, 4,389 edges, 2.0 MB `graph.json` | 2,223 nodes, 4,057 edges |
| Build wall time ⚠ one run | 4.9 s | 2.9 s, plus the `gfortran -E` pass |
| Modules `W3SRCE`'s file `USE`s, per the graph `(v)` | `constants`, `w3dispmd`, `w3gdatmd`, `w3idatmd` | the four, plus `w3sbt1md`, `w3sdb1md`, `w3sln1md`, `w3snl1md`, `w3src4md` |
| `calls` edges, of which across files `(v)` | 752, 0 | 656, 0 |
| `graphify query "who calls W3SDS4"` `(v)` | the definition only, `w3src4md.F90` L1831; no caller | the same |
| `graphify path W3SRCE W3SDS4` `(v)` | no path | no path |
| `grep -in "call *w3sds4" *.F90` `(v)` | 7 call sites in 4 files, among them `w3srcemd.F90:1303` | |

Three things follow. The `USE` graph is right only after preprocessing: `w3srcemd.F90` has 239
`#ifdef` lines `(v)` `grep -c '^#ifdef' w3srcemd.F90`, and on the raw tree every `USE` behind a
switch is lost, so the graph silently drops `W3SRCE`'s dependence on `W3SRC4MD` and `W3SNL1MD`, the
two modules this repository ports. On the preprocessed tree the list is the one the lab build
compiles. Second, graphify's Fortran extractor resolves calls only inside one file; it does not
answer #68's questions (a) "every caller of `W3SDS4`" or (b) "the path from `W3WAVE` to `W3SNL1`",
and `grep` answers (a) in one command. Third, nothing in either pass left the machine: the AST pass
makes no model call `(v)` run under `env -i` with no API key and `OLLAMA_BASE_URL` pointed at a
closed port.

The sister project took the same tool on for symbol lookup across its repositories and measured
the same shape of result: 3 of 8 real questions answered, every miss about wiring the tool does not
see, and plain `git grep` cheaper whenever the keyword is known `(v)` marola MIP-0076 §2 and its
2026-10-10 revision, read 2026-10-11.

### Decision

**Graphify is adopted for one job: listing the module dependencies (`USE`) and the symbols a WW3
file defines, built offline from the sources preprocessed for a named switch at the pinned commit.
It is a way to find which files to open, never a source: a WW3 fact is still cited as
`model/src/<file>.F90:<line>` read from the file, and "who calls X" is still answered with `grep`.**
Its installers, hooks, strict mode, MCP server and model-backed passes are not used.

The adoption is done in these steps, in this order. Each is a PR with its own gates; the record
moves to Accepted when step 1 has a result the owner accepts, and the steps after it are not
started before that.

1. **Finish #68's evaluation on the preprocessed graph.** The three questions of #68 §3, each
   answered with the graph and without it, compared with `file:line` read by hand, tokens and wall
   time as a median of three runs with the harness named. Question (b) is expected to fail and is
   reported as such; (a) is asked of the graph and of `grep`. Results go in a new dated log entry and
   in a *Results* section of this record. If the graph does not beat reading files on (c), the
   module-variable question, this record is Rejected with the numbers and no later step runs.
2. **`scripts/graph.sh` and a `just graph` recipe**, shell only, `set -euo pipefail`, shellcheck
   clean, with `--self-test` and `--dry-run`:
   - `graph build [switch]` preprocesses `$WW3/model/src` (default the `WW3` submodule) with
     `gfortran -E -cpp -P` and `-DW3_<token>` for every token of the switch file (default
     `switches/switch_lab_shrd`), then runs `graphify extract . --code-only --no-label` on the result.
     Both the preprocessed tree and the graph go to
     `${XDG_CACHE_HOME:-$HOME/.cache}/ww3-gpu-graph/<ww3-sha>-<switch>/`, never into the checkout. It
     writes `build.json` there with the WW3 SHA, the switch file and its hash, and the graphify
     version. An uninitialised submodule or a dirty WW3 tree is an error.
   - Every graphify call runs under `env -i` with only `PATH`, `HOME` (the cache), `GRAPHIFY_OUT`,
     `GRAPHIFY_NO_AUTO_REFRESH=1` and `OLLAMA_BASE_URL=http://127.0.0.1:9`, and under `unshare -rn`
     where user namespaces allow it, as marola MIP-0076 §5.2 does. The script never passes
     `--backend` and refuses `extract` without `--code-only`.
   - `graph query|explain` pass the cached `graph.json`, default `--budget 400`, and print a
     staleness line when the WW3 SHA or the switch differs from `build.json`. `graph path` is not
     wrapped, since it cannot find a call path across files.
3. **Pin the tool.** graphify is run as `uvx --from graphifyy==<version>`, the mechanism `just
   specify` already uses, with the version in one variable in `scripts/graph.sh`. When
   `picasso/labs/pratico` carries the nixpkgs `graphify` package, the pin moves there in a
   `picasso` PR and the `uvx` line goes ⚠ until then: `uvx` pins the version, not the wheel's hash.
   An update is a PR that re-runs step 1's question (c) and records the graph size.
4. **Keep its output out of git and out of context.** `graphify-out/` goes in `.gitignore`, and
   `.claude/settings.json` denies `Read(**/graphify-out/**)` and `Read(**/GRAPH_REPORT.md)`, so an
   accidental in-tree run neither enters a commit nor fills a session. `graphify install`,
   `graphify hook install` and `--strict` are named in `CONTRIBUTING.md` as not to be run here.
5. **State the rule where agents read it.** One sentence in `AGENTS.md`, "WW3 source is read-only",
   and its longer form in `CONTRIBUTING.md`: `just graph` finds files, a claim cites the file at the
   pin, a graph result is never quoted as evidence and is `⚠` until the file is opened. The same
   sentence goes in `docs/AGENTS_KOKKOS_202609.md` §1, where porting agents look, and a row in the
   gates table of `AGENTS.md` (`bash -n`, `shellcheck`, `scripts/graph.sh --self-test`).
6. **Glossary.** Entries for Graphify and tree-sitter in `docs/GLOSSARY.md` with the first use, and
   ADR-0007 in "This repository's own names", with their remissive index lines.
7. **No skill until it earns one.** If sessions keep reaching for the graph, a skill that says when
   to use `just graph` and when `grep` is cheaper is written here or ported from marola-devkit's
   `routing` skill with `sharingan`, pinned in `skills.lock` with its audience `.patch`. Graphify's
   own `/graphify` skill is not installed, because its installer writes outside the lock.
8. **No CI job.** CI does not check out WW3 and the graph is never committed, so there is nothing to
   keep current; `scripts/graph.sh --self-test` runs where the other script self-tests run.

### Alternatives considered

| Option | Why not |
|---|---|
| Adopt it as #68 first sketched, on the raw tree, as a call graph for the port planner (#42) | Measured above: on the raw tree the `USE` edges behind a switch are missing, and on either tree there is no call across files. A planner fed from it would miss exactly the routines being ported. |
| Index this repository too | 337 tracked files, already linked by the WFIP index, the figure gallery and the glossary (#68 §2, Pros 1); `grep` and the indexes answer faster. |
| Run graphify's semantic pass on `docs/`, `pubs/` or WW3's manual | It sends the text to a model provider and costs tokens (#68 §2, Cons 5), and its inferred edges are a second, unreviewed reading of documents that already carry `(v)`. |
| Install the `/graphify` skill and the hooks, as upstream recommends | The installer writes assistant configuration outside `skills.lock`; strict mode blocks the first file read, which pushes an agent to trust the graph over the file, the opposite of `(v)` (#68 §2, Cons 3 and 4). |
| Reuse marola-devkit's `graph` tool directly | It indexes the checkout it runs in and knows nothing of switches or preprocessing; this repository is not a devkit flake consumer, only of its reusable workflows. The envelope is copied, the tool is not. |
| Commit `graph.json` | 2 MB per switch and pin, stale the moment the pin or the switch moves; the pin has already drifted from the text once (#68 §2, Cons 1). |
| Reject it now | The preprocessed `USE` graph is correct for the lab switch and builds in seconds, and question (c) of #68 is unanswered; one day of evaluation is cheaper than a guess either way. |

### Consequences

- A porting session can ask "what does `W3SRCE` depend on under `switch_lab_shrd`" and get the
  compiled answer in seconds, then open only those files. The answer for a different switch needs a
  different build, by construction.
- Callers, call paths and the arrays a routine writes are still found by reading and `grep`. The
  graph does not make the port planner (#42) automatic.
- The repository gains one shell script, one recipe and a third-party Python tool fetched at run
  time, pinned by version. Nothing in the lab code, the kernels or CI depends on it, and deleting
  the script undoes the adoption.
- A graph result never appears in a document as evidence; reviewers treat a citation that names
  the graph instead of a `file:line` as a defect.
- graphify releases about daily (marola MIP-0076 §4); the version pin and step 3's re-run keep an
  update from changing answers silently.

### Revisit when

- graphify's Fortran extractor resolves calls across modules (a `calls` edge whose ends are in
  different files on the preprocessed tree): then the call-graph use and the port planner join are
  reconsidered in a new record.
- Step 1's evaluation finishes: this record gains *Results* and moves to Accepted or Rejected.
- WW3 is built by CMake with a `compile_commands.json` that names the preprocessed sources, which
  would replace the `gfortran -E` pass in step 2.
- The WW3 pin moves to a branch whose switches change which modules `W3SRCE` uses.
- WW4 (C++/Kokkos) becomes a porting reference here; its tree is a different question.

### Revision, 2026-10-14: this repository's own code

The owner widened the scope on 2026-10-14 to this repository's code as well, for two Claude Code
commands: `/graph-check` (is the CLI installed, and how far behind) and `/graph-view` (prepared
queries over `kokkos/`, `scripts/`, `tests/` and the rest). The alternative "Index this repository
too" above is set aside for code only; the Markdown stays out, as does the semantic pass. The rest
of the envelope holds: `--code-only --no-label`, `env -i` with `GRAPHIFY_NO_AUTO_REFRESH=1` and a
closed `OLLAMA_BASE_URL`, output under `~/.cache/ww3-gpu-graph/self-<sha>/`, `graphify-out/` in
`.gitignore`, and a graph result is a lead to a file, never a citation. The measurement, including
what the graph misses, is the [log entry of 2026-10-14](log/2026-10-14-graphify-on-ww3-gpu.md).

graphify's `/graphify` skill exists on the owner's workstation from a user-level `graphify install`
outside this repository (v) `~/.claude/skills/graphify/SKILL.md`, 0.9.91, 14 October 2026; step 7
still holds for the repository: nothing here installs it, and `graphify-out/` stays out of git.

### Contexto

O responsável trabalha neste repositório a partir de um projeto do Claude Code ("Projects") na

- **Sessões na nuvem existem no Team.** "Cloud sessions are available on Pro, Max, and Team plans,

  ([Cloud](https://code.claude.com/docs/en/claude-code-on-the-web)). No Team, uma sessão pode ser

  desligá-las para todos.
- **Segredos de rede não existem no Team.** No ambiente da nuvem, "Team and Enterprise plans don't
  have them yet"; variáveis de ambiente ficam visíveis a quem usa o ambiente
  ([Cloud](https://code.claude.com/docs/en/claude-code-on-the-web), "Security and isolation").
- **O mais próximo de um projeto compartilhado no Team é o Claude Tag**, o Claude nos canais do

  organização ([Claude Tag](https://claude.com/docs/claude-tag/overview)). A página de Projects o

- Os "Projects" do chat do claude.ai, pastas de conhecimento, são outro produto e existem em todos
  os planos; não estão em discussão aqui.

O que o projeto tem e o que acontece com cada parte, pelo retrato do ADR-0005 e pelas fontes acima:

| Instruções do projeto | serviço | sim | estão vazias `(v)` [`project.json`](../.claude/project/project.json), lido em 2026-10-09; se ganharem texto, ele é copiado do retrato |
| Prompts das rotinas | serviço, com cópia em `.claude/project/routines/` | o texto sim, a rotina não | recria-se a rotina na conta Team a partir do arquivo; a rotina antiga continua na conta pessoal |

### Decisão

**O repositório é o veículo da portabilidade. Tudo o que um colaborador do LOSUFBA precisa para
trabalhar com agentes neste repositório vive em git e funciona em qualquer sessão Claude Code,
de qualquer plano. O projeto pessoal continua sendo onde o responsável coordena o trabalho, e só
é recriado na organização Team quando o Team tiver Projects.**

1. Nenhuma regra de trabalho mora só no projeto. Instruções, preferências e lições que valem para
   o LOSUFBA entram em `AGENTS.md`, `CLAUDE.md`, uma skill ou um documento, por PR. As instruções
   do projeto continuam vazias, e a memória, desligada.
2. Na organização Team, os colaboradores usam sessões na nuvem, a CLI ou o app de desktop no mesmo
   repositório, com os mesmos hooks e gates. O ponto de encontro entre as duas contas são issues e
   PRs no GitHub, como entre os dois projetos da lição 19. Sessões que o grupo precisa ver são
   compartilhadas com visibilidade **Team**.
3. Cada rotina roda numa conta só. Uma rotina que o grupo precise na conta Team é recriada lá a
   partir do prompt em `.claude/project/routines/`, e a da conta pessoal é desligada no mesmo dia,
   para que nenhuma issue seja respondida duas vezes nem nenhum PR de dependências saia em dobro.
4. Antes de qualquer troca de conta, os arquivos do projeto que servem de referência entram no
   repositório, e os artefatos que outras pessoas leem vão para o GitHub Pages.
5. Quando Projects chegar ao Team, cria-se o projeto na organização seguindo
   `.claude/project/README.md`, atualiza-se o retrato com o novo `read_on`, e o projeto pessoal é
   arquivado, não apagado, enquanto alguém ainda consultar suas threads.
6. Nada pago é ligado na organização Team por causa desta decisão (Claude Tag, créditos de uso,
   assentos) sem confirmação explícita do responsável e do Owner da organização.

### Alternativas consideradas

| Opção | Por que não |
|---|---|
| Compartilhar o projeto pessoal com os colaboradores | Impossível: um projeto é de um usuário só e não tem compartilhamento `(v)`. |
| Dar aos colaboradores acesso à conta Max | Uma conta pessoal é de uma pessoa; tudo o que ela faz no GitHub e nos conectores sai em nome do responsável `(v)` [Routines](https://code.claude.com/docs/en/routines), e compartilhar credenciais contraria os termos de uso ⚠ (não conferido no texto dos termos). |
| Mover todo o trabalho para o Team agora e abandonar o projeto | Perde-se a coordenação de threads, a visão geral e as rotinas ligadas ao projeto, sem ganho para os colaboradores, que já recebem pelo repositório tudo o que é portátil. |
| Adotar o Claude Tag no Slack como substituto do projeto | É o produto de equipe que mais se parece com um projeto, mas exige um workspace Slack pareado, um Owner e um saldo de uso da organização; não foi avaliado para este grupo e é custo novo. Fica como opção a revisitar. |
| Exportar memória, threads e arquivos por script | Não há exportação nem API fora de uma sessão do próprio projeto (ADR-0005, "Alternatives considered"), e a memória está desligada. |
| Esperar o Team ter Projects e não fazer nada até lá | Os colaboradores ficariam sem as regras e gates enquanto isso, quando o repositório já os entrega hoje. |

### Consequências

- Um colaborador do LOSUFBA que clona o repositório recebe as mesmas regras, hooks, skills e o
  revisor da proposta que as threads do projeto recebem, sem depender da conta pessoal.
- O responsável continua sendo o único que vê as threads do projeto. O que o grupo precisa saber
  sobre elas chega por PR, issue ou pelo painel de andamento.
- Regras que hoje um agente poderia guardar na memória do projeto passam a exigir um PR. É mais
  lento, e é o que a regra de evidência do repositório já pede.
- Duas contas podem disparar o mesmo tipo de automação; o item 3 da decisão é o que evita
  respostas em dobro, e depende de disciplina, não de uma verificação automática.
- A migração futura do projeto é um procedimento à mão, como no ADR-0005, e o retrato pode estar
  desatualizado no dia em que for usado; `read_on` diz de quando ele é.

### Revisitar quando

- A documentação de Projects deixar de dizer que o recurso não está no Team ou no Enterprise.
- Projects ganhar compartilhamento, controles de organização, exportação ou transferência entre
  contas.
- O Team ganhar segredos de rede no ambiente da nuvem, o que muda como uma rotina guarda chaves.
- O grupo decidir usar Slack, o que torna o Claude Tag uma alternativa a avaliar com custo medido.
- O ADR-0006 ([PR #96](https://github.com/h0ffmann/ww3-gpu/pull/96)) for aceito e parte das regras
  sair deste repositório para um submódulo.

## ADR-0010: The Kokkos port has no tests of its own; WW3's regtests are its only tests

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-14 |
| **Deciders** | Hoffmann |
| **Written by** | Hoffmann, with an agent |
| **Scope** | How a ported routine is validated: the L1 unit tests of the port (`kokkos/tests/L1_test_snl1_*`, `shim_roundtrip`, their fixture generators), the `googletest` column of `kokkos/ports.tsv`, the coverage measurement, and the parity rule behind a timing. Not the tests of the course's intro programs or of the lab's tools (`nccmp-tol`, `bench_case`, `fetch_analyse`), which test no port. Not the proposal's text |
| **Related** | [WFIP-0003](WFIPs/WFIP-0003-kokkos-regtest-matrix.md) (the WW3 regtest matrix that replaces the L1 evidence); [`docs/AGENTS_KOKKOS_202609.md`](AGENTS_KOKKOS_202609.md) §1.5 (the validation contract this changes); [`AGENTS.md`, "Porting"](../AGENTS.md#porting-hard-rule); [ADR-0002](#adr-0002) (port order, unchanged) |

### Context

The owner, 2026-10-14, verbatim: "implement WFIP-003, now, A single PR, step by step, use
subagents, now kokkos code should NOT have its own tests, hard rule. All tests should come com WW3
regtests". Asked what happens to the existing tests, the owner chose to remove the port's own tests
and keep those that test no port.

Until that day a port was "done" with an L1 GoogleTest against a fixture captured from the verbatim
Fortran, then an L2 replay inside WW3 (`AGENTS_KOKKOS_202609.md` §1.5, items 3 and 4). For
`W3SNL1` and `INSNL1` the L1 tests showed bit-identity, max relative error 0.0, on serial-debug and
openmp-release `(v)` (`just kokkos-test`, 14/14, 2026-10-14) and on cuda-release `(v)`
(`bench/results/snl1-i9-14900-rtx4090-2026-09-15.json`, `l1`). The L2 replay ran one WW3 regtest,
`ww3_ts1`, judging `hs` only `(v)` (CI health h1, 2026-10-15 01:34 UTC, the evening of 14 October in Brazil).

The L1 fixture is the lab's own capture of the Fortran, a second copy of the reference
(`snl1_ref.F90`) next to WW3's; WW3's regtests are the cases NOAA runs on the code as it ships.

### Decision

**Kokkos code in this repository has no tests of its own. A ported routine is validated only by
WW3's regression tests, run inside WW3 built from the h0ffmann/WW3 fork with the routine on Kokkos,
and compared with the same WW3 built without it.** The tests are `scripts/ww3-gpu.sh --ww3-gpu --cpu`,
pair to pair with `--ww3` (CI health h1), and the matrix of WFIP-0003 (`scripts/hoff_matrix.sh`):
every serial `NL1` entry of `regtests/bin/matrix.base`, compared by WW3's `test.comp` and by
`nccmp-tol` within `kokkos/tools/nccmp-tol/tolerances.txt`. If WW3's regtests agree for the
Fortran routine and for its Kokkos translation, the routine is ported. They run on the CPU (Kokkos
on OpenMP): no `--ww3-gpu --gpu` run is part of validating a port (`AGENTS.md`, "Running on the
GPU").

In this repository that means:

1. The port's L1 tests, the `shim_roundtrip` driver and the fixture generators (`snl1_ref.F90`,
   `snl1_sea_state.F90`, `gen_snl1_fixture.F90`, `gen_snl1_ww3lib.F90`) are deleted, with the
   `snl1-fixtures` and `l1-crosscheck` recipes. The committed `snl1_nk25_nth24.bin` stays, frozen,
   as the input of the kernel benchmark `ww_bench_snl1` and of `proof/snl1_cons`.
2. The status ladder of `kokkos/ports.tsv` is `ported → L2 → gpu`; `L1` is gone. The `googletest`
   column is removed; `regtested` stays and is required.
3. `scripts/kokkos_coverage.py` and `docs/data/kokkos_coverage.tsv` are removed: they measured
   what CTest runs of the port, and CTest no longer runs the port.
4. "No timing without parity" now means a passed WW3 regtest replay on the same commit. A
   `bench/results/` record carries `regtest: passed: <command>`; the record of 2026-09-15, whose
   parity was the L1 of its day, stays as history.
5. A new port (`/port-next`) scaffolds the kernel, the shim, the port report and the ledger row,
   and no test file.

### Alternatives considered

| Option | Why not |
|---|---|
| Keep the L1 tests beside the regtests | The owner's rule; and two references of the same Fortran drift apart unseen |
| Keep them, but stop adding new ones | Offered; the owner chose removal |
| Remove every CTest, the intro and tool tests too | Offered; those test a lesson or a tool, not a port, and stay |

### Consequences

- One reference: the Fortran WW3 ships, through the harness NOAA uses. No second copy to keep in
  step.
- The bit-identity evidence of the kernel alone is history, not a gate. L2 is not byte-identical
  even on `ww3_ts1` (`docs/PORT_ASSESSMENT_202610.md` §4), so the remaining check is a tolerance
  check, and it judges only the fields each regtest writes.
- A defect in the kernel shows up later and larger: a regtest run is minutes, an L1 test was a
  fraction of a second, and a failure points at a model run, not at one call.
- The CUDA kernel has no check at all until a regtest runs on the GPU, which is the owner's,
  supervised (`AGENTS.md`, "Running on the GPU").
- The proposal promises "per-routine unit tests with captured inputs" for deliverable D4
  (`docs/WFIPs/README.md`, "Proposal deliverables"). That text is not changed here; it goes to the
  owner and the proposal's reviewer.
- The course chapters that taught the L1 tests (lessons 07, 08, 10 to 14), the glossary, the
  dated plans and the port reports are rewritten to this rule in the same change, keeping the L1
  results as dated history ([`docs/log/2026-10-14-kokkos-regtests-only.md`](log/2026-10-14-kokkos-regtests-only.md)).

### Revisit when

- A regtest on the GPU is supervised and passes: then the `gpu` status is reachable again.
- The matrix finds a defect that a test of one call would have located faster.
- WW3 itself gains unit tests a port could run against.

#### What the regtests found, and what that means for this decision

All three defects of the `W3SNL1` port were found by WW3's regtests inside WW3, at `-O3`: the
AF11 power expansion (the L1 fixtures, built at `-g`, could not see it), the OpenMP nesting
abort (OMPG entries) and the single-grid shim (`ww3_multi` entries) (v, the logs above). A later
regtest still finds these defects. It finds them later, and in a larger diff. The decision
below accepts that cost and adds the controls that keep it small.

### Decision

**A port step is a unit: a physics package or a group of routines that WW3 calls together, such
as all of ST4 (`w3src4md.F90`). Inside a unit, the routines are translated with discipline and
without regtests. WW3's regtests run at checkpoints: after a big move in the codebase, and when
the unit is finished.** ADR-0010 is unchanged: the regtests remain the only tests of the port,
and nothing is "ported", L2 or timed without them.

#### Checkpoints

A checkpoint runs `just smoke`, `just full-ww3-gpu` and `just ww3-gpu-matrix <jobs> all` for the
switch of the unit, on the CPU. A checkpoint is due at each of these events, and before the next
one starts:

1. a port unit is finished (all its routines translated and wired);
2. the `WW3/` pin moves, or the fork branch changes the caller hunks;
3. the toolchain changes: a picasso (`nix-config`) bump, a new gfortran, Kokkos or CUDA;
4. the memory contract changes, such as phase 2 (device-resident spectrum);
5. before any status in `kokkos/ports.tsv` moves to L2, before any timing enters a table, before
   a release, and before a GPU run under the owner's supervision.

Between checkpoints, a change to Kokkos code needs only the build gates of `AGENTS.md`
(`just kokkos-test serial-debug`, `just kokkos-test openmp-release`, the CUDA preset compiled).
CI keeps health h1 on every pull request, unchanged.

#### The discipline that replaces the per-routine regtest

1. **One run-time flag per routine**, all off by default (`WW_KOKKOS_SNL1`, `WW_KOKKOS_SDS4`, and
   so on). A unit is never the default path before its checkpoint passes, and a failing
   checkpoint is bisected by turning on one flag at a time.
2. **The `-O3` object code is read before the translation.** A first task lists every power,
   folded constant and reduction order of the unit from gfortran's `-fdump-tree-optimized`, with
   WW3's own Release flags. This is the AF11 lesson, applied before the code exists.
3. **A line-by-line translation review** by a fresh reviewer for each routine, against the
   Fortran at the pin, before the routine is committed. It reads; it runs nothing.
4. **Bit parity is argued statically between checkpoints**, by the route
   [ADR-0001](#adr-0001) accepted: a comparison of the optimised GIMPLE
   (`-fdump-tree-optimized`) of the Fortran routine, built with WW3's Release flags, and of the
   C++ kernel, built with the `openmp-release` flags. For each routine it shows the same `float`
   operations in the same order, the same libm calls (`expf`, `logf`, `powf`, `__powisf2`), the
   same constants after folding, and no FMA. A difference is a defect of the port, fixed before
   the commit, or a question to the owner. This is evidence read from the compilers, not a test
   of the port and not a fixture (ADR-0010). A helper of one `float` input (an integer power
   tree, a table lookup) may also get ADR-0001's exhaustive sweep over all 2^32 inputs, kept under
   `proof/` beside `proof/snl1_cons`, never in CTest. It covers the host build only: CUDA's device code and
   libm are outside it. The port report records it as "static parity, ⚠ until the checkpoint";
   the checkpoint remains the verdict.
5. **One commit per routine, in profile order** (ADR-0002), so a checkpoint failure maps to a
   small set of commits.
6. **Every quirk of the Fortran is listed in the plan and kept**, with one comment line in the
   kernel that cites the source line.
7. **The ledger says the truth between checkpoints**: status `ported`, `regtested` = `no:
   waiting for the checkpoint of <unit>`, every parity claim ⚠, no number in a table.
8. **A checkpoint failure stops new translation** until the failure is explained, in a
   `docs/log/` entry.

### Consequences

- A port unit goes from plan to checkpoint in days, not weeks. ST4 is planned as one 8-hour
  translation session ([`ST4_KOKKOS_PLAN_202610.md`](ST4_KOKKOS_PLAN_202610.md)).
- A defect shows up later, in a larger diff. The per-routine flags, the commit order and the
  `-O3` inventory are what keep the search small. If a checkpoint failure takes longer to locate
  than the regtests it saved, the unit was too large; the next plan makes it smaller.
- Long stretches of code sit at status `ported`, unvalidated. The flags default to the Fortran, so
  no user of the fork runs unvalidated code unless they turn a flag on.
- `AGENTS.md` (the gate table and "Running on the GPU"), `CONTRIBUTING.md`, `/port-next` and the
  `ww3-port` skill are changed to this cadence in the same pull request.
- Bit for bit, "no timing without parity", ADR-0002's order and the GPU rule do not change.

### Revisit when

- A checkpoint failure takes more than one working day to locate.
- The matrix gets fast enough (a shared build cache, a second machine) that a run per routine
  costs less than 15 minutes.
- The first two units have passed their checkpoints: then record here how long each took, and how
  many defects each checkpoint found.

### Decision

**A translated unit is accepted into the tree on static parity and one fresh review; it is wired
into WW3 behind its `WW_KOKKOS_*` flag, off by default, and verified by building WW3 with it. The
full WW3 regtest matrix of the translated units runs on the UFSC H100 node, on its host CPUs
(`--ww3-gpu --cpu`), not on the i9. The i9 keeps the CPU smoke and full runs (`just smoke-ww3-gpu`,
`just full-ww3-gpu`, pair to pair with `--ww3`) for when the owner calls a checkpoint: a finished
wiring batch or a move of the `WW3/` pin.** The owner's "no regtests for now" (2026-10-16)
applies until he calls one.

1. **Static parity and one review are the bar for a translation.** As ADR-0011 items 2 to 6: the
   `-O3` inventory before the code, a line-by-line review by a fresh reviewer against the Fortran
   at the pin, the GIMPLE and object comparison, one commit per routine. Nothing new is asked.
2. **Wired and not regtested is a legitimate state.** A row whose Kokkos code WW3 calls behind its
   flag has `wired` "yes: <where>" and `regtested` "no: <why>" in `kokkos/ports.tsv`, and the
   port score counts it at the *ported* level, never at *regtested* (`scripts/port_score.py`).
   Wiring is verified by building: WW3 with the `KOKKOS` switch configures, compiles without a
   new warning on a line of the hunks, and links; `just kokkos-test serial-debug` and
   `openmp-release` pass; the CUDA preset compiles.
3. **`WW_KOKKOS_ALL=1` on wired-but-not-regtested parts is for development, not for results.**
   Its output is not evidence of parity, does not enter a table, and is not quoted as "100 %
   Kokkos" without the words "of the wired parts, not regtested".
4. **The matrix is the verdict and nothing skips it.** No status moves to L2, no timing enters a
   table, no release claims a part, and no row's `regtested` becomes "yes" on the strength of the
   matrix without the matrix having run on the same commit with `WW3GPU_STRICT=ON`, every entry
   whose switch has the routine's switch. The bit-for-bit rule binds every one of those runs.
5. **On the H100 node the matrix runs on the CPU first.** The matrix driver has no GPU path, and
   a `--ww3-gpu --gpu` run needs the owner supervising it (`AGENTS.md`, "Running on the GPU"). The
   node serves the matrix for its host cores and because the i9 is the working machine, not for
   its GPU; how many cores it has is not recorded ⚠.

#### The modes: FULL, PARTIAL and the default

What runs on Kokkos is chosen at run time; the build is the same (v, `PATCH.md` §7 at the wiring
change, read 2026-10-16).

| Mode | How it is set | What runs on Kokkos |
|---|---|---|
| Default | no `WW_KOKKOS_*` variable set | nothing: every part is the Fortran (0 % Kokkos), since 2026-10-14 |
| PARTIAL | `WW_KOKKOS_<PART>=1` for each part wanted (`WW_KOKKOS_SNL1`, `_SDS4`, `_SIN4`, `_SPR4`, `_ST4_TABLES`, `_SRCE`, `_GATH`, `_SCAT`, `_UWND`, `_UTRN`, `_DZXY`, `_MAP3`, `_MAPT`, `_DISTAB`, and the ST0 to ST6, FLX and SWL parts) | the listed parts |
| FULL | `WW_KOKKOS_ALL=1` | every wired part whose translation covers the switch file; a part that does not cover it stays Fortran |
| Explicit off | `WW_KOKKOS_<PART>=0` | that part is the Fortran, whatever `WW_KOKKOS_ALL` says |

One function, `ww_kokkos_flag` (`kokkos/src/fortran_iface/part_flags.cpp`), resolves every flag
for the shims and for `W3KOKKOS_SETUP`, so the Fortran and the C++ cannot disagree; `W3INIT`
writes one "Kokkos parts" line to `log.ww3` naming where each part ran. FULL means 100 % of the
wired parts: 87.6 % of the run time of the committed profile at the wiring change, with
propagation, I/O and set-up still Fortran (`python3 scripts/port_score.py --write` on that
branch, v 2026-10-16).

`scripts/ww3-gpu.sh --ww3-gpu <case> --kokkos all|none|<PART,...>` sets `WW_KOKKOS_ALL=1`, `=0`,
or `=0` plus the listed parts in the Kokkos run, gives the Fortran run `WW_KOKKOS_ALL=0`, and
prints the parts line and the per-part call counters. Without `--kokkos` it keeps
`WW3GPU_ROUTINES` (default `SNL1`).

The regtest matrix has a PARTIAL selection today: `WW3GPU_ROUTINES=<R>,<R>,... just
ww3-gpu-matrix <jobs> <serial|omp|mpi|all>` selects every `matrix.base` entry whose switch has the
physics word of one of the routines and sets `WW_KOKKOS_<R>=1` for them in the Kokkos run, every
flag 0 in the Fortran run (`regtests/CMakeLists.txt:19-22`, the routines of
`WW3GPU_ALL_ROUTINES`, `regtests/cmake/ww3gpu_common.cmake:52`). It knows the source-term

### Relation to ADR-0011

This ADR narrows ADR-0011's checkpoint rule; it does not supersede it, unless the owner says it
does. ADR-0011 runs `just smoke`, `just full-ww3-gpu` and `just ww3-gpu-matrix <jobs> all` at each
checkpoint. Under this ADR the matrix part of a checkpoint moves to the H100 node and waits for
it, and the i9 runs the smoke and the full when the owner calls the checkpoint. ADR-0011's
discipline (flags off by default, the `-O3` inventory, the fresh review, static parity, one
commit per routine, the ledger telling the truth) applies unchanged, and so does its item 5: L2,
a timing, a release and a GPU run each still wait for the matrix. ADR-0011's "Revisit when"

| Option | Why not |

### Consequences

#### What crosses between host and device

Phase 1 moves one sea point per call. `W3SRCE`'s shim copies the point's spectrum, `WN`, `CG`
and its scalars to the device, runs the kernel, and copies them back, and the Fortran caller
serialises the calls under `!$OMP CRITICAL (WW_KOKKOS_SRCE)` (v,
`kokkos/src/fortran_iface/srce_shim.cpp:5-10,111-115`); `W3SNL1`'s and ST4's shims do the same
per call (v, `snl1_shim.cpp:376-384`, `st4_shim.cpp:369-385`). On a GPU each call is therefore
about ten host-to-device and device-to-host copies of a few kilobytes and one kernel launch, for
one point's work, which a GPU runs on a single thread. Each of those costs microseconds of fixed
latency before any arithmetic, and the points never run side by side, so a phase 1 GPU run is
expected to be slower than `--ww3`, not faster ⚠ (an argument from the shims' structure; no
timing of `--ww3-gpu --gpu` exists, and none may be taken without parity).

Two things follow for which parts are worth routing to a GPU:

- **One unit, not its pieces.** Routed one by one inside a Fortran `W3SRCE`, `SNL1`, `SDS4`,
  `SIN4` and `SPR4` each make their own round trip per point and per source-term sub-step.
  `SRCE` routed as a whole makes one round trip per point per time step and keeps the DIA and ST4
  on the device between them (its kernel reads the `W3SNL1` and ST4 tables of the grid,
  `srce_shim.cpp:9-10`). On a device build, `SRCE` is the part to route; the separate flags are
  for bisecting a difference on the CPU.
- **Batches, not points.** The transfer only pays when a call carries every sea point of the
  grid, or when the spectrum stays resident between time steps (phase 2,
  [`H100_OPTIMIZATION_STRATEGY_202610.md`](H100_OPTIMIZATION_STRATEGY_202610.md)). Until then
  no part has a transfer cost a GPU can win back.

### Decision

From its acceptance by the owner on 2026-10-16, and for each part only once the conditions below hold for it, the
default (part flag unset, `WW_KOKKOS_ALL` unset) becomes on for `SRCE` in a device (CUDA) build,
and for `SNL1`, `SDS4`, `SIN4`, `SPR4`, `ST4_TABLES` and `SRCE` in a host (OpenMP) build. Every
other part stays off by default. An explicit
`WW_KOKKOS_<PART>=0` or `WW_KOKKOS_ALL=0` still selects the Fortran, so `--ww3-gpu`'s Fortran run
and every comparison of the matrix keep the Fortran in the same executable.

1. **Checkpoint.** The part's row of `kokkos/ports.tsv` says `regtested` yes, from the WW3 regtest
   matrix of ADR-0012 with `WW3GPU_STRICT=ON` on the entries that compile the part's switch.
2. **Timing with parity.** A record in `bench/results/` on the target machine, on the same
   commit as a passed regtest replay, shows `--ww3-gpu` with the part on faster than `--ww3`,
   median of three runs, end to end (`scripts/results.py check` refuses it otherwise).
3. **On a GPU, a batched shim.** The device default needs `SRCE`'s shim to carry all sea points
   of a call, or the spectrum to stay resident (phase 2), and the GPU run's bits to match the
   Fortran's (`AGENTS.md`, "Bit for bit", the `expf`/`logf` caveat), under the owner's
   supervision.

The PR that flips a default edits the default list in `part_flags.cpp`, names the record of
condition 2, and updates ADR-0011's rule 1 by a superseding note, not by an edit.

The PR1, PR2 and unstructured explicit propagation parts (`XYP1`, `KTP1`, `XYP2`, `KTP2`,
`XYPUG`) are outside this decision: they are opt-in only, ignored by `WW_KOKKOS_ALL`, by the
owner's request of the same day.

### Alternatives considered

- **Flip the defaults now, without regtests.** What was asked first. Rejected for now: five of the
  six parts have no `regtested` yes in the ledger, and a default that changes a bit changes every
  run built with the switch; no measurement says the GPU run is faster.
- **Keep ADR-0011's all-off default for good.** Keeps every run the Fortran unless asked, but makes
  the operational configuration a list each user has to know; `--kokkos all` already turns on
  parts outside NOAA's physics.
- **A named opt-in list (`--kokkos ops`) instead of a default.** Smaller, and possible as a first
  step; it does not give the "no flag set" run the owner asked for.

### Consequences

- Nothing changes until a part meets both conditions: today every default is the Fortran.
- Once a part flips, a `--ww3-gpu` build with no flag set runs it on Kokkos; reproducing the
  Fortran from that build needs `WW_KOKKOS_ALL=0`, and `scripts/ww3-gpu.sh` already sets it for the
  Fortran run.
- NOAA's operational switch is `DIST MPI`; the `W3GATH`/`W3SCAT` Kokkos path covers only `SHRD`
  (PATCH.md), so the default list holds no support routine.

### Revisit when

- the H100 matrix (ADR-0012) has run, or the first `bench/results/` record of `--ww3-gpu --gpu`
  exists;
- propagation (`W3XYP3`, `W3KTP3`) is wired, since it is the next cost after the source terms;
- GEFS-Wave's switch is read and differs from `switch_NCEP_st4`.

## ADR-0014: A GPU run is judged by nccmp-tol's tolerances; the CPU backend stays bit for bit

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-17 |
| **Deciders** | Hoffmann |
| **Written by** | Hoffmann, with an agent |
| **Scope** | The verdict of a `--ww3-gpu --gpu` run (and of `just ww3-gpu-matrix-cuda`) against the Fortran of the same executable and against `--ww3`, and so whether its timing may enter a table. Not the CPU backend, whose rule is unchanged; not the tolerances themselves; not the GPU supervision rule |
| **Related** | AGENTS.md, "Bit for bit with the Fortran" (its GPU paragraph, which this ADR answers); [ADR-0010](#adr-0010); [ADR-0013](#adr-0013) (its condition 3); [`kokkos/tools/nccmp-tol/tolerances.txt`](../kokkos/tools/nccmp-tol/tolerances.txt); [`bench/README.md`](../bench/README.md) |

### Context

AGENTS.md says a GPU port that cannot be bit for bit with the Fortran stops and asks the owner.
It cannot be, at known sites:

- ST4 reproduces glibc's vector math at five loops of `w3src4md.F90` (`:316`, `:317`, `:2315`,
  `:2500` with `powf`, `:2509` with `expf`); "on a device there is no libmvec ... such a build
  cannot be bit for bit at these sites" (v, `kokkos/src/ww_kokkos/st4_libmvec.hpp:10-13`).
- On CUDA, `logf`, `tanhf`, `sincosf`, `expf` and `powf` come from NVIDIA's libdevice, whose bits
  against glibc are not known (v, `kokkos/src/fortran_iface/PATCH.md`, the parity column of the
  run-time flags table).

The owner was asked on 2026-10-17 how GPU runs are judged, and chose the tolerances of
`nccmp-tol`, with bit for bit kept for the CPU backend.

### Decision

1. **CPU backend (Serial, OpenMP): unchanged.** Bit for bit with the Fortran of the same
   executable; `test.comp` finding a file different fails, as AGENTS.md says.
2. **GPU backend (CUDA): the verdict is `nccmp-tol` with `tolerances.txt`**, as the L2 replay
   already runs it, against the Fortran of the same executable and against `--ww3`. A field the
   file lists passes when every value meets its `abs` or `rel` bound; a run passes when every
   listed field does. The run also prints `max|d|`, the rms and the largest relative difference
   of every field, listed or not, and the record keeps them.
3. **Never widened.** A tolerance is not changed to make a GPU run pass. A change to
   `tolerances.txt` is its own pull request, reviewed by a person (AGENTS.md, "Never cheat a
   regtest tool"), with the evidence for the new bound.
4. **A GPU timing enters a table** only after such a pass on the same commit, and its record says
   "GPU: judged by tolerance, not bits" in `regtest`.

### Alternatives considered

- **Bits only, GPU diagnostic.** Keeps one rule for every backend, and stops all GPU performance
  work until a device math library with glibc's bits exists, which no plan foresees.
- **Decide after the first supervised run.** Sees the differences before ruling, and leaves
  every GPU number unquotable meanwhile; this ADR keeps that option as its first review.

### Consequences

- The ST4 libmvec sites and the libdevice calls are expected to differ by a few ULP per step; how
  much that grows over a run is unknown until the first supervised run ⚠.
- `tolerances.txt` judges five fields (`hs`, `fp`, `dir`, `dp`, `t0m1`). The smoke writes 26
  variables and judges one of them, `hs` ("1 judged, 25 unlisted"); the full case judges `hs` of
  five (v, the runs of 2026-10-16 and 2026-10-17). An unlisted field is reported, not judged ⚠:
  judging more fields is a change to `tolerances.txt` under point 3.
- `scripts/results.py record` writes the wording of point 4 in the `regtest` of a CUDA record.
- AGENTS.md, "Bit for bit with the Fortran", states this rule in place of "stops and asks the owner".

### Revisit when

- the first supervised `just perf-ww3-gpu full 3` has run: read its `nccmp-tol` table, every field;
- a device math library with glibc's bits, or a reimplementation of the five libmvec loops and
  the libdevice calls with glibc's algorithms, exists;
- a field outside `tolerances.txt` shows a difference that matters to a reader of the output.

## ADR-0015: Triton kernels are allowed as an exception to "no Python in lab code", under three conditions

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-17 |
| **Deciders** | Hoffmann |
| **Written by** | Hoffmann, with an agent |
| **Scope** | Whether a GPU kernel written in Triton may enter this repository's lab code, which AGENTS.md otherwise limits to C++, Fortran and shell. Not the Kokkos port, not repo tooling, not the GPU parity rule (ADR-0014) |
| **Related** | issue #171 (Triton trial ports), issue #45 (`W3SDS4` in Triton); [ADR-0010](#adr-0010); [ADR-0014](#adr-0014); [ADR-0002](#adr-0002) |

### Context

AGENTS.md: "Lab code is C++, Fortran and shell. Python appears only in the publishing and repo
tooling (`scripts/*.py`, `tests/`), never in lab code or kernels." Triton is "a language and
compiler for parallel programming" with "a Python-based programming environment" for writing
kernels (v, https://triton-lang.org/main/index.html, read 2026-10-17), so a Triton kernel is
Python. Issue #171 asked the owner how to treat that; the owner answered on 2026-10-17: allow
Triton kernels as an exception, if better fitted for the problem, if they can be integrated with
the Fortran/C++ code, and if they can be regtested.

### Decision

A Triton kernel may enter lab code when all three hold, each shown in its pull request:

1. **Better fitted.** For the routine it ports, it beats the Kokkos kernel of the same routine on
   the same GPU, kernel-only and end to end, median of three runs after parity (`bench/README.md`),
   or it does something the Kokkos port cannot (#45's GEMM form of the cumulative term is the
   example on record). Otherwise the routine stays in Kokkos.
2. **Integrated.** WW3 calls it through the same kind of path as a Kokkos part: a `bind(C)` shim
   behind a `WW_KOKKOS_*`-style run-time flag that defaults to the Fortran, the Fortran routine
   kept selectable at run time, the memory contract written down. Whether that needs a Python
   interpreter at run time, or a kernel compiled ahead of time and launched from C, is shown in the
   pull request ⚠ (not checked on 2026-10-17).
3. **Regtested.** It is validated as the Kokkos port is (ADR-0010): by WW3's regtests, the Fortran
   against the Triton routine in one executable, judged on the GPU by `nccmp-tol`'s tolerances
   (ADR-0014). No test of its own replaces that.

Everything else in AGENTS.md applies unchanged: translate, don't improve; reductions keep the
Fortran's order unless the owner decides otherwise in its own pull request; GPU runs only under
the owner's supervision.

### Alternatives considered

- **Python only at build time.** Keeps the rule intact, and depends on an ahead-of-time route whose
  existence is not checked ⚠; condition 2 still prefers it where it exists.
- **Triton as a scratch study outside the lab code.** Safe, and leaves any good result unusable by
  WW3.

### Consequences

- AGENTS.md's language rule names this exception.
- A Triton kernel that fails any condition stays in a study branch or a `docs/log/` entry, never in
  lab code.

### Revisit when

- the first Triton kernel meets, or fails, the three conditions (#171, step 3);
- Triton's ahead-of-time route is checked.

## ADR-0016: The goal is WW3's run time on Kokkos and CUDA; WW3's regtests move to a later validation phase; one person works in a short compound loop

| | |
|---|---|
| **Status** | Accepted (its Compound Engineering clause superseded by [ADR-0021](#adr-0021)) |
| **Date** | 2026-10-17 |
| **Deciders** | Hoffmann |
| **Written by** | Hoffmann, with an agent |
| **Scope** | What the repository optimises for, when WW3's regtests run, how a speed figure is reported before they run, and how engineering work is planned, done, reviewed and remembered (`AGENTS.md`, `CONTRIBUTING.md`, `.compound-engineering/config.yaml`, `.claude/settings.json`). Not WW3 read-only, not "translate, don't improve", not bit for bit as the target, not the GPU supervision rule, not the proposal's reviewer, not the CI gates |
| **Related** | Supersedes [ADR-0011](#adr-0011) (regtests at checkpoints); keeps [ADR-0010](#adr-0010) (WW3's regtests are the port's only tests) and [ADR-0002](#adr-0002) (port order by wall time); agrees with [ADR-0012](#adr-0012) (Proposed: the matrix on the H100); [ADR-0013](#adr-0013) and [ADR-0014](#adr-0014) unchanged |

### Context

The owner, 2026-10-17, verbatim: "the main goal of the repository is to speed up WW3 runtime with
Kokkos e CUDA. All the enginering framework should be adopted with this in mind. Regtests
postponed, will validate if the translation from Fortran to C++ was accurate. It's a 1 person
project so it needs eng. pattern with agility." The same day: "adopt compound-engineering-plugin,
and make sure AGENTS will follow its pattern when guided by me to do eng. work".

ADR-0011 ran WW3's regtests at every checkpoint: a finished unit, a pin or toolchain move, before
L2, before a timing, before a release. AGENTS.md also refused any speed figure without a passed
regtest replay on the same commit. With one person, a busy shared workstation and the CUDA
matrix gated on the owner's presence, those gates set the pace of the whole project: the same
`--ww3` run took 22.6 s to 361.7 s on this machine during the W3OUTG work ⚠ (a timing survey in
that session, no record in `bench/results/`).

Compound Engineering (EveryInc, MIT) is a Claude Code plugin of 36 skills built around one loop:
brainstorm, plan, work, simplify, review, compound (v, its `README.md` at
`compound-engineering-v3.30.3`, read 2026-10-17). Its last step writes what a solved problem
taught into a folder that the next plan reads.

### Decision

1. **The goal.** The repository exists to make WW3 run faster with Kokkos and CUDA, without
   changing the Fortran's arithmetic. A change is judged first by the wall time it removes from a
   WW3 run, and the port order stays the measured profile's (ADR-0002).
2. **Regtests postponed.** WW3's regtests (`just smoke-ww3-gpu`, `just full-ww3-gpu`,
   `just ww3-gpu-matrix`) no longer run at each checkpoint. They run in a validation phase the
   owner calls, and that phase answers one question: was the translation from Fortran to C++
   accurate, bit for bit on the CPU (ADR-0010), within ADR-0014's tolerances on a GPU. Until then a
   row of `kokkos/ports.tsv` keeps `regtested` as "no: postponed (ADR-0016)", and nothing becomes
   default-on (ADR-0013 still asks for its checkpoint).
3. **Between now and that phase,** translation accuracy is argued statically, as ADR-0011 already
   allowed between checkpoints: the `-O3` GIMPLE or disassembly of the Fortran and the C++, and,
   for device math, `libm_bits` against glibc. CI's gates and `health.yml` keep running.
4. **Speed figures before the regtests** may be measured and reported in a pull request, a port
   report, a log entry or a plan, each marked "regtest pending ⚠" with machine, command and the
   median of three runs. The tables generated from `bench/results/` keep their gate
   (`scripts/results.py check` refuses a timing without `regtest: passed`); changing that gate is a
   person's review, as every gate is.
5. **The loop.** Engineering work the owner asks for follows Compound Engineering's loop, sized to
   the change: small changes skip the plan, medium ones plan and review, large ones brainstorm
   first. The plugin is enabled in `.claude/settings.json` pinned to `compound-engineering-v3.30.3`;
   its artifacts live under `docs/compound/` (`docs_root` in `.compound-engineering/config.yaml`).
   Where a step clashes with a hard rule, the rule wins and `AGENTS.md`, "Engineering work", says
   how the step is redirected.
6. **Tools that serve the goal**, adopted in the same change: Context7 (Upstash, MIT) as a plugin,
   for current Kokkos, CUDA and CMake documentation; Archify (tt-a1i, MIT) as a pinned submodule,
   not a copy, for interactive twins of the repository's Mermaid figures.

### Alternatives considered

- **Keep ADR-0011's checkpoints.** Safest for the bit-for-bit claim; rejected by the owner because
  the regtest schedule, not the translation, set the pace.
- **Drop the regtests.** Rejected: they are the only evidence the translation is right (ADR-0010),
  and the speed goal is worthless if the answer changes.
- **A heavier process (a WFIP for every change, an issue before any work).** Built for several
  contributors; for one person it costs more than the review it buys. WFIPs stay for changes that
  move a proposal deliverable.
- **No framework, ad hoc sessions.** What each session learned stayed in that session; the
  compound step is the part that fixes this.

### Consequences

- A speed figure can appear before its parity is known; the "regtest pending ⚠" mark is what keeps
  it honest, and a later regtest failure invalidates every figure measured on that code.
- The validation phase carries more risk at once: a translation error found there may sit under
  several units of work. Static parity on each routine is what bounds it.
- Agents follow one named loop, so the owner can say "plan it", "work it", "review it", "compound
  it" and get the same steps every session.
- Two plugins and one vendored skill more to keep pinned; Context7 sends queries to Upstash's
  server, so a query never carries a secret or unpublished text.

### Revisit when

- The owner calls the validation phase and it reports: then decide whether regtests return to
  checkpoints.
- A regtest finds a translation error that static parity missed.
- A second regular contributor joins.

## ADR-0017: The Kokkos port is single node; an MPI build of WW3 keeps the Fortran path

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-18 |
| **Deciders** | Hoffmann |
| **Written by** | an agent, from the owner's answer of 2026-10-18 ("Out of scope, write ADR"); accepted by the owner the same day |
| **Scope** | Which parallel layouts of WW3 the Kokkos runtime supports: the shared-memory one (`SHRD`, with or without `OMPG`/`OMPH`) on the CPU and on one GPU. Not the physics switches each part covers, not the GPU parity rule ([ADR-0014](#adr-0014)) |
| **Related** | [ADR-0016](#adr-0016); [ADR-0013](#adr-0013); [`KOKKOS_H100_PLAN_202609.md`](KOKKOS_H100_PLAN_202609.md); [`H100_OPTIMIZATION_STRATEGY_202610.md`](H100_OPTIMIZATION_STRATEGY_202610.md); [`PRODUCTION_READINESS_202610.md`](PRODUCTION_READINESS_202610.md); [the 2026-10-18 regtest log](log/2026-10-18-resident-regtest-lab-switch.md) |

### Context

WW3 runs in one of two layouts, chosen by switch. With `SHRD` one process holds the whole
spectrum `VA(NSPEC,NSEA)`, and `OMPG`/`OMPH` split its loops over threads. With `DIST MPI` each
rank holds the spectra of its own sea points. Spatial propagation then moves one component at a
time between ranks: `W3GATH` gathers it into `FIELD`, `W3XYP3` propagates it, and `W3SCAT` sends
it back, with persistent MPI requests around the loop (`model/src/w3wavemd.F90:2040-2149` at
`WW3@80644ba9`).

The port was designed for the first layout. The plan lists `W3GATH`, `W3SCAT` and `IAPPRO` under
"Delete; identity mappings" (`KOKKOS_H100_PLAN_202609.md`, §4). The goal is WW3's run time with
Kokkos and CUDA on this lab's machine and one H100 (ADR-0016), and the strategy says "A
single-H100 WW3 serves this lab's use" (`H100_OPTIMIZATION_STRATEGY_202610.md`, top of the page).

The 2026-10-18 validation found where that design stops (v, read at `WW3@80644ba9`):

- Four of the six parts of `--kokkos resident` cover `SHRD` only: `XYP3`
  (`model/src/w3kokkos_prop3md.F90:127-129`), `OUTG` (`w3kokkos_outgmd.F90:61-66`), `IOPE`
  (`w3kokkos_pntmd.F90:49-54`) and `UPDV` (`w3kokkos_updvmd.F90:57-62`). Asked for by name on an
  MPI switch, each stops the model (`w3kokkosmd.F90:1188`, `KOKKOS_PART`).
- The measured gain of the resident preset comes from keeping `VA` on the Kokkos side between
  steps. Under MPI the exchanges stay in Fortran and read and write the host `VA` once per
  component, so an MPI path that keeps the gain needs device-side gathers and scatters or
  CUDA-aware MPI. A per-component `W3XYP3` on `FIELD` would be bit for bit but not fast ⚠ (not
  built or timed).
- NOAA's GFS-Wave runs with MPI on CPU nodes (`H100_OPTIMIZATION_STRATEGY_202610.md`, "How NOAA
  runs WW3"). Operations at a centre are therefore the use that MPI would serve.

### Decision

The Kokkos runtime supports the shared-memory layout only: `SHRD`, with or without `OMPG` or
`OMPH`, on the CPU (Kokkos OpenMP or Serial) and on one GPU. An MPI build of WW3 runs the Fortran
for every part that covers `SHRD` only. It stops when such a part is asked for by name, as it
does today. No MPI path is translated, wired or regtested in this repository while this ADR stands.

### Alternatives considered

- **MPI in scope, phase A ("MPI works").** `W3XYP3` alone on `W3GATH`'s `FIELD`, one component per
  call, with `W3GATH` and `W3SCAT` left in Fortran, then regtested on MPI entries. Bit for bit is
  within reach, since the C++ already separates the propagation from the shared-memory gather.
  Rejected for now: it adds an untimed path that does not serve the goal. A prototype was written
  and discarded on 2026-10-18.
- **MPI in scope, full ("MPI is fast").** Device-side gathers and scatters, or CUDA-aware MPI, with
  the resident `VA` kept across the exchanges. Rejected for now: a large unit, needed only for a
  centre's operations or for several GPUs.

### Consequences

- The regtest matrix's resident selection needs `SHRD` and has no MPI entry
  (`regtests/CMakeLists.txt`, `WW3GPU_SWITCH_WORDS`). The 43 MPI entries deferred by the CPU
  validation plan are out of scope, not pending.
- A speed figure of this repository is a single-node figure. No page may claim the port is
  ready for an operational centre's MPI runs. Gap 3 of `PRODUCTION_READINESS_202610.md` stays
  open by decision.
- Single-node gaps stay in scope. The most pressing is `ww3_multi` writing the host `VA` between
  `W3WAVE` calls without a sync (`PRODUCTION_READINESS_202610.md`, gap 2), because it applies to
  `SHRD`.
- Several GPUs would also need MPI (one rank per GPU), so this ADR also limits the port to one
  GPU per run.

### Revisit when

The owner sets operational use at a centre, an upstream WW3 runtime that must cover NOAA's
switches, or more than one GPU per run as a goal. A new ADR then supersedes this one and starts
from the "MPI is fast" alternative, since a path that is not fast does not serve those goals
either.

### Decision

None yet. This ADR records the three options with the evidence above, for the owner and, if it
comes to that, for WW3's maintainers to choose from. What the evidence supports today:

- Option (a) is what exists and was built end to end on 2026-10-18: install-only configure,
  install, WW3 built against the prefix, `smoke` byte-identical pair to pair
  (`PRODUCTION_READINESS_202610.md`, gap 5).
- Options (b) and (c) were not built. Their costs below are read from the files, not measured ⚠.

### Alternatives considered

#### (a) An external package WW3 finds (today's layout)

WW3 keeps `find_package(ww_kokkos <major.minor> REQUIRED)` behind `-DWW_KOKKOS=ON`; `ww_kokkos` is
released and installed on its own, like NetCDF or ESMF.

- The upstream diff is the Fortran half only: 4 082 new and 819 changed lines of Fortran, 64 lines
  of CMake, one `switches.json` category.
- The C++ keeps its own repository, licence files, CMake minimum (3.25; WW3 asks for 3.19, v,
  `WW3/CMakeLists.txt:4`) and C++20 requirement, and its own release cadence.
- Two version contracts must move together: WW3's `find_package` minimum and the ABI version of
  `ww_kokkos`. Today a WW3 commit that needs a new entry point raises the minimum by hand.
- An operational centre installs one more library, built against the same Kokkos as its WW3; the
  `EXACT` check makes a mismatch a configure error instead of a link-time surprise.
- WW3's exported targets name `ww_kokkos::ww_kokkos` (`ww3_lib` links it `PUBLIC`), so a consumer
  of an installed WW3 must find the package too ⚠ (no consumer built).
- Licence: the LGPL-derived kernels are distributed from a repository whose top licence is MIT,
  each file with its own line. Whether that is enough is the question marked ⚠ above.

#### (b) A submodule of WW3

WW3 adds `ww_kokkos` as a git submodule at a pinned commit and builds it with `add_subdirectory`
or `ExternalProject_Add` when `KOKKOS` is set.

- WW3 has no submodule at the pin (v, no `.gitmodules` in `WW3/`); this would be its first, with
  `git clone --recurse-submodules` in every build recipe that uses the switch.
- The gitlink pins the C++ exactly, so the two-version problem of (a) becomes one commit; the
  `find_package` minimum is no longer needed.
- `add_subdirectory` brings this tree's CMake 3.25 minimum and C++20 into WW3's configure, and the
  install-only option is what keeps GoogleTest and NetCDF out of it. `ExternalProject_Add` keeps
  the trees apart at the cost of a second configure step ⚠ (neither built).
- The C++ stays in its own repository with its own licence files, as in (a).
- Who maintains the submodule's repository, and who may move the gitlink, is a governance
  question WW3's maintainers answer, not this repository.

#### (c) Sources inside `model/src`

The C++ is copied into WW3, for instance `model/src/kokkos/`, and built by WW3's CMake.

- The upstream diff grows by about 58 000 lines of C++ in 347 files, about 14 times the 4 082 new lines of the Fortran half.
- One repository, one version, one licence file: the LGPL-derived kernels would sit in an LGPL
  project. The 22 MIT files would sit in it too ⚠ (whether WW3 accepts MIT files, or relicences
  them, is for its maintainers and a legal reading).
- WW3's CMake would need C++ in its languages, the contraction flags (`-ffp-contract=off`,
  `--fmad=false`) on the C++ sources only, and the CUDA `libm` table generator; today those live
  in `kokkos/src/ww_kokkos/CMakeLists.txt`.
- The lab's tools and intro programs stay here; the port's validation is WW3's regtests in every
  option (ADR-0010), so no test suite moves.
- Every change to the C++ becomes a WW3 pull request; this repository would then track WW3 for
  the C++ as it does for the Fortran.

### Consequences

Whatever is chosen:

- The Fortran half is upstream's in every option; its 819 changed lines are what a reviewer reads,
  and with `KOKKOS` off they compile to the original (`PRODUCTION_READINESS_202610.md`, gap 12).
- The licence of the files without an `SPDX` line has to be settled before any option ships ⚠.
- The `EXACT` Kokkos check stays: in (b) and (c) the Kokkos is still an external package, and a
  build against another Kokkos still links code compiled for one Kokkos with another's runtime.
- Gap 12 stays a Blocker for target (b) of `PRODUCTION_READINESS_202610.md` until an option is
  accepted. Gap 5's configure dependencies are closed by the install-only option; its other
  items (a static archive only, C++20, CMake 3.25) remain.

### Revisit when

The owner opens a conversation with WW3's maintainers about taking the runtime, or a legal reading
of the licence question is available, or WW3 adds submodules or C++ for another reason.

## ADR-0019: GoogleTest for the runtime infrastructure that ports no WW3 routine

| | |
|---|---|
| **Status** | Proposed |
| **Date** | 2026-10-18 |
| **Deciders** | Hoffmann |
| **Written by** | an agent, from the owner's question of 2026-10-18 ("is it possible to adopt GoogleTests in this repository, as an alternative way to test?") and the code review of PR #191 |
| **Scope** | Which C++ of `kokkos/` may have GoogleTest suites of its own: the runtime infrastructure (the resident spectrum's state machine and column caches, the run-time flags, presets and fallback counters, the package config). Not a ported routine, not its shim's arithmetic, not the Fortran half on the fork, not the scripts (they keep their `--self-test`s) |
| **Related** | [ADR-0010](#adr-0010) (which this narrows, never loosens, for ported routines); [ADR-0016](#adr-0016); [plan 006](plans/2026-10-18-006-googletest-runtime-infrastructure-plan.md); [`kokkos/tests/CMakeLists.txt`](../kokkos/tests/CMakeLists.txt) |

### Context

ADR-0010 (Accepted, 2026-10-14) removed every unit test of a ported routine: a GoogleTest of a
routine needs a fixture captured from the Fortran, a second copy of WW3's arithmetic that drifts
from the one WW3's own `-O3` build computes (gfortran expands `x**11` differently at `-O0` and
`-O3`, [`docs/log/2026-10-14-snl1-bitwise-af11.md`](log/2026-10-14-snl1-bitwise-af11.md)). Its
title reads wider than its alternatives table: "Kokkos code in this repository has no tests of its
own", while it kept the tests "that test no port" (`kokkos/tests/CMakeLists.txt` at `main`
`5cd0140`: `L1_test_intro`, `L1_test_nccmp_tol`, `L1_test_bench_case`, `L1_test_fetch_analyse`,
`L1_test_timers`, all GoogleTest, run by `just kokkos-test` and CI's `kokkos` job, v).

Since then the port grew code that ports no WW3 routine and that every resident run depends on
(v, sizes at `5cd0140`, `wc -l`):

| File | Lines | What it decides |
|---|---|---|
| `kokkos/src/fortran_iface/resident_shim.cpp` | 599 | which copy of `VA` (host or device) holds the newer bits, every copy between them, the column reads and writes of `ww3_multi`, the output readers and `W3CPRT`, the per-grid column-list cache (`kMaxColSets = 8`), `WW_KOKKOS_VA_CHECK`, `_POISON`, `_RESIDENT`, `_COUNT` |
| `kokkos/src/fortran_iface/part_flags.cpp` | 135 | `ww_kokkos_flag` (a part's flag, the preset, `WW_KOKKOS_ALL`, the opt-in list), `WW_KOKKOS_PRESET`, `WW_KOKKOS_STRICT`, the fallback slots and the line printed at exit that the regtest driver reads |

A defect there changes no arithmetic: it hands a kernel stale bits, copies the wrong columns, or
lets a run report Kokkos while the Fortran ran. WW3's regtests catch it only when the stale bits
reach a compared file, and the review of PR #191 found such gaps (the report of run
`20261018-154456-d3a4d3cf`: the `W3OUTG` fallback outside strict mode, the missed-sync check off by
default, the column cache that can thrash, `WW_KOKKOS_STRICT` on only for the literal `1`). Each
has a known right answer that needs no Fortran reference.

### Decision

**Ported routines keep ADR-0010 unchanged: no unit test, no fixture, WW3's regtests are their only
tests. The runtime infrastructure that ports no WW3 routine may have GoogleTest suites of its own,
which test its contract through its public C ABI on a host backend (Serial, OpenMP), never on a
device without the owner, and never as parity evidence for a ported routine.**

In this repository that means:

1. A suite is allowed for code that computes nothing WW3 computes: the residency state machine, the
   column lists and their cache, flag, preset and strict-mode parsing, fallback slots and the exit
   lines, the package config. A file that translates a WW3 routine, or a shim's arithmetic around
   one, has none.
2. Suites call the C ABI the Fortran calls (`resident_c.hpp`, `ww_kokkos_c.hpp`); no test-only
   entry point is added to production code. A behaviour that depends on an environment variable
   read once per process gets its own CTest entry with that `ENVIRONMENT`.
3. Suites are named `infra_test_<area>` and carry the CTest label `infra`, so that a reader of
   `ctest -N` can tell them from the tool tests, and a CUDA build can exclude them (`-LE infra`)
   until the owner runs them on a device.
4. A suite enters only with evidence that it can fail: each test is shown, on a scratch copy, to
   fail against a planted defect in the code it guards (the method of the mutation audit of
   2026-10-17).
5. `just kokkos-test serial-debug` (sanitizers, bounds checks) and `openmp-release` run them, as
   CI's `kokkos` job does today; no new gate.

### Alternatives considered

| Option | Why not |
|---|---|
| Keep ADR-0010 as read, no new suite | Leaves the infrastructure that decides every copy of the spectrum with no test faster than a regtest, and the review's gaps found by reading only |
| GoogleTest for ported routines too | ADR-0010's reason stands: a captured fixture is a second, drifting copy of WW3's arithmetic |
| Test hooks in production code (reset the state, peek at the device copy) | A hook is code the Fortran never calls; the public ABI is enough (plan 006, "How the state machine is observed") |
| Bash or CMake tests instead | The scripts keep theirs; the C++ state machine is best driven from C++ |

### Consequences

- A defect of the residency logic or of a flag rule shows in a fraction of a second, at the
  function, before a regtest run.
- ADR-0010's rule for ported routines is unchanged and now stated against a boundary; if this ADR
  is accepted, ADR-0010's index row gains "narrowed by ADR-0019", and `AGENTS.md` ("The port has no
  tests of its own"), `CONTRIBUTING.md` and the `ww3-port` skill say where the boundary is.
- Infrastructure suites add maintenance: a change of the C ABI's contract changes its suite in the
  same PR.
- On a CUDA build the suites would run kernels on the device, so they stay out of any agent's CUDA
  ctest (label `infra`), as the device rule requires.

### Revisit when

A suite catches nothing over several months of changes to its file, or a defect of the
infrastructure reaches a regtest first: then the boundary or the suite is wrong.

## ADR-0020: MPI enters the Kokkos port, with the exchange built on the resident spectrum

| | |
|---|---|
| **Status** | Proposed |
| **Date** | 2026-11-01 |
| **Deciders** | Hoffmann |
| **Written by** | an agent, from the owner's words of 2026-11-01: "MPI will be implemented anyway, just tests required postponed until I get back to my i9 rtx 4090 workstation" |
| **Scope** | Which parallel layouts the Kokkos runtime supports, and how a `DIST MPI` build moves the spectrum. Not the physics each part covers, not the GPU parity rule ([ADR-0014](#adr-0014)), not when regtests run ([ADR-0016](#adr-0016)) |
| **Related** | Supersedes [ADR-0017](#adr-0017) once accepted. Plan: [`2026-11-01-002-mpi-kokkos-plan.md`](plans/2026-11-01-002-mpi-kokkos-plan.md). Analysis: [`OPEN_MP_VS_MPI_202610.md`](OPEN_MP_VS_MPI_202610.md), [`PRODUCTION_READINESS_202610.md`](PRODUCTION_READINESS_202610.md) sections 3 and 11 |

### Context

ADR-0017 kept the port on `SHRD` and said "No MPI path is translated, wired or regtested in this
repository while this ADR stands". Its "Revisit when" asks the next ADR to start from the "MPI is
fast" alternative, because a path that is not fast does not serve the goal. The owner has now put
MPI in scope. Three things follow from reading the pin, `WW3@96892c95` (v, 2026-11-01):

- **The largest unwired costs need MPI.** `PDLIB_JACOBI_GAUSS_SEIDEL_BLOCK` and
  `CALCARRAY_JACOBI_VEC` are 37.54 % and 20.37 % of the `pdlib` profile. `PDLIB` requires `MPI`
  (`model/src/cmake/switches.json:769-770`), and all 16 regtest switch files naming it have `MPI`.
  NOAA's GFS-Wave switches are `DIST MPI` too (`model/bin/switch_NCEP_st4`).
- **The exchange does no arithmetic.** Under `W3_MPI`, `W3GATH` and `W3SCAT` copy `REAL`s
  (`w3wavemd.F90:3293-3598`, `:3614-3913`), and each component starts from `FIELD = 0.` above both
  arms (`:3427`). So the order and grouping of the messages cannot change a bit of the propagation
  of one component, provided every value arrives where the Fortran puts it. One case is not yet
  settled: `SSTORE` is not cleared, and `W3SCAT` skips `MAPSTA = 0` points (`:3776`) ⚠, so the
  plan's unit M2 must show no sea point is in that state or reproduce the buffer.
- **The Fortran's exchange is bound to the host.** The persistent requests of `W3MPIP` name
  `VA(ISP,1)` (`w3initmd.F90:2013-2016`) and `GSTORE`, `SSTORE` (`:2036-2037`, `:2073-2076`), with
  only `MPIBUF = 6` buffers (`w3adatmd.F90:379`). This is what ties the exchange to one component
  at a time and to the host array.

### Decision

1. **`DIST MPI` is in scope.** Parts are translated and wired for it, one flag per part as today,
   and an MPI build may run them. Where a part does not yet cover `MPI`, the Fortran runs, as now.
2. **The MPI path keeps `VA` resident across the exchange.** The batched path packs and unpacks on
   the Kokkos side and aggregates one step's components into one message per pair of ranks. A
   per-component `W3XYP3` on `W3GATH`'s `FIELD` is not built: ADR-0017 weighed it, and it would
   copy the spectrum between host and device on every step.
3. **`ww_kokkos` stays free of MPI.** The MPI calls stay in the fork's Fortran, in a new module
   behind the `KOKKOS` switch; the shim packs, unpacks and hands buffer addresses over `bind(C)`.
   This keeps `ww_kokkos_c.hpp`'s "Phase 1 is deliberately MPI-free" and the package of ADR-0018.
4. **An exchange message is not a sync.** The rule "No full-spectrum copy to keep the copies in
   sync" (AGENTS.md, "Resident spectrum") is about copies made to keep host and device consistent.
   The values MPI must carry between ranks are the model's own communication, and the bytes are
   the Fortran's. They move out of the Kokkos-side `VA` directly, never through a whole-array
   host read, and `WW_KOKKOS_VA_COUNT=1` reports them on their own line, so that the whole-spectrum
   copies per step do not grow.
5. **Code before tests, flags off.** Units merge with the gates and the static argument of
   ADR-0016, every MPI path is off unless asked for by name, and `WW_KOKKOS_ALL` does not turn one
   on. No part defaults to Kokkos under MPI (ADR-0013) until its entries pass the matrix on the
   owner's i9-14900 and RTX 4090 workstation. The rows say `regtested` `no: postponed (ADR-0016)`.
   The plan keeps the list of what that session must run.

### Alternatives considered

- **Per-component `W3XYP3` with `W3GATH`, `W3SCAT` in Fortran ("MPI works").** Smallest change and
  bit for bit within reach. Rejected as the destination for the reason in ADR-0017. Its first half
  survives as unit M1: the parts that already compile under `MPI` get run.
- **Move the existing persistent requests to device buffers.** Keeps the Fortran's message pattern
  and needs CUDA-aware MPI from the start. Rejected: `MPIBUF` buffers still force one component at
  a time, which defeats the one launch per step that gives the measured gain.
- **MPI calls in C++.** Rejected: `ww_kokkos` would link MPI in every build, including the
  `SHRD` ones, and the package ADR-0018 keeps simple would need an MPI compiler wrapper.
- **`PDLIB` first.** It is the largest share of any committed profile. Rejected as the first unit
  only: ADR-0002 orders by the operational case, GFS-Wave runs structured grids, and the
  aggregated exchange is shared by what follows. It is scheduled, unit M6.

### Consequences

- ADR-0017's "single-node figure" limit stays true of every number already published. A page may
  claim MPI only after the regtest pass, with its ranks stated.
- The 43 MPI entries of the CPU validation plan return from "out of scope" to "pending". Gap 3 of
  `PRODUCTION_READINESS_202610.md` reopens.
- Code merges that no test has run. That is ADR-0016's bargain and is why decision 5 keeps every
  path off, but the first run of each unit will find defects the static argument missed ⚠.
- An MPI path may not end up faster than the Fortran on a GPU. The aggregated exchange removes
  host copies and message counts, not the bandwidth of the interconnect, and no timing of it exists
  ⚠. If the workstation's numbers say so, this ADR is what to revisit.
- More than one GPU per run becomes reachable (unit M8), and with it the device-per-rank problem of
  `PRODUCTION_READINESS_202610.md` section 3.

### Revisit when

The first timed comparison on the workstation shows the aggregated exchange slower than the
Fortran's per-component one on the same ranks, or the first matrix pass finds a bit difference
that message aggregation causes.
